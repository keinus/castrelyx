## 실험 결과와 적용 판정

**Laya를 빠른 보안 판단기로 사용하는 방향은 계산 속도 측면에서 타당하지만, 이번 모델로 실제 자동 차단의 정확성과 효과까지 입증하지는 못했습니다.** 학습과 실제 로그 처리 코드는 동작합니다. 그러나 공개 공격 표본에서 누락·오탐이 남고, 합성 시험에서 관계 특징을 지워도 정답률이 유지됩니다. 따라서 현재 산출물은 후속 실험에 사용할 프로토타입이며, 관계가 있어야만 알 수 있는 이상을 신뢰성 있게 찾아 대응하는 완성 모델은 아닙니다.

### 학습한 내용

2026-10-04, 서버의 RTX 4090 24GB 한 장에서 Laya root 영어 모델을 사용했습니다. 학습 상태 사례는 2,179개, 각 사례에 방책·긴급도·위협 여부 질문을 부여한 항목은 6,537개입니다. ModernBERT 인코더와 판단 헤드 약 421M 파라미터를 전체 미세조정했고 사용하지 않는 보조 act_head만 동결했습니다. 이는 지도학습 교차엔트로피 학습이며 원 모델의 RLCD 재현이나 비지도 이상탐지 학습이 아닙니다.

인코더 학습률 1e-5, 헤드 5e-5, AdamW, micro batch 4, 8회 누적, 3 에포크/615회 업데이트를 사용했습니다. validation 315개로 체크포인트를 선택하고 calibration 296개로 질문 종류별 온도를 보정했습니다. policy_validation 312개로 보류 문턱을 선택했고 test 304개는 마지막 평가에만 사용했습니다. 최대 길이는 1,024 토큰이며 모든 split의 입력 잘림 검사를 통과했습니다. 학습에서 가장 긴 입력은 560 토큰입니다.

온도 보정 포함 학습 시간은 670.43초입니다. 선택된 체크포인트는 3번째 에포크이며 마지막 scorer 가중치의 변화량 L2는 0.03305입니다. 원본과 학습 모델의 SHA-256이 다르고 저장된 가중치를 다시 읽어 평가했습니다. 근거는 `runs/training_complete.json`, `runs/training_history.json`, `models/security-sft/training_metadata.json`, `runs/artifact_inventory.json`입니다.

### 정확도는 자료별로 해석해야 한다

아래 방책 일치율은 사람이 설계한 정책 라벨과의 일치율입니다. 대응 후 공격 성공률을 측정한 수치가 아닙니다. 모든 숫자는 정책 보류 이전의 모델 출력 기준입니다.

| 시험 자료 | 사례 수 | 원본 방책 일치율 | 학습 후 방책 일치율 | 학습 후 위협 정밀도 / 재현율 |
|---|---:|---:|---:|---:|
| 공개 CIC 흐름 요약 | 128 | 1.56% | 94.53% (121/128) | 62.50% / 62.50% |
| 합성 결합 시나리오 | 176 | 7.39% | 100.00% (176/176) | 100.00% / 100.00% |

CIC 시험에는 공격 상태가 8개뿐입니다. 5개 탐지, 3개 누락이며 정상 상태 120개 중 3개를 위협으로 오탐했습니다. 오탐률은 2.5%이고, 재현율의 사례 단위 Wilson 95% 구간도 약 30.6~86.3%로 넓습니다. 이 구간조차 같은 수집 캠페인에 속한 사례 간 의존성을 보정하지 않은 기술 통계입니다. 새로운 환경 성능에 대한 보장으로 사용할 수 없습니다.

항상 정상이라고 답하는 기준선의 CIC 위협 정확도는 93.75%이고 학습 모델은 95.31%입니다. 항상 OBSERVE를 고르는 기준선의 방책 일치율은 93.75%여서 학습 모델의 94.53%는 0.78%p 높은 데 그칩니다. 공개 표본에서 QoS 방책 정답 2개는 모두 FLOW_DROP으로 잘못 선택했습니다. 정상 상태를 FLOW_DROP으로 고르면서 확신도 0.942를 반환한 사례도 있습니다. 따라서 높은 확신도만으로 자동 제어를 허용해서는 안 된다는 구체적 오류가 관측됐습니다.

전체를 섞은 방책 일치율은 97.70%지만 합성 자료의 쉬운 패턴이 크게 기여하므로 이를 실환경 탐지 성능으로 제시하지 않습니다. 분할 기준, 정답과 예측의 혼동표, 개별 오류는 `runs/benchmark.json`, `runs/results_summary.json`, `runs/predictions_finetuned.jsonl`에서 확인할 수 있습니다. 비교는 같은 입력과 질문·최대 길이를 사용한 원본/파인튜닝 모델 사이의 비교이며, Zeek 규칙·통계 탐지기·다른 LLM보다 우월하다는 시험은 수행하지 않았습니다.

### 결합 입력의 효과와 관계 추론의 효과는 다르다

| 합성 시험의 입력 제거 실험 | 방책 일치율 |
|---|---:|
| 모든 입력 사용 | 100.00% |
| 호스트 특징·이벤트·관계 제거, 네트워크와 자산 문맥 유지 | 33.52% |
| 네트워크 특징·관계 제거, 호스트와 자산 문맥 유지 | 87.50% |
| 관계 특징만 제거 | 100.00% |

이 결과는 현재 모델이 호스트 정보에 많이 의존한다는 근거이며, 명시적인 로그 관계 특징이 최종 분류에 필수라는 근거는 아닙니다. 제거 실험은 학습 분포 밖의 입력을 만드는 민감도 시험이므로 제거 후 점수 차이를 곧바로 관계 추론의 인과 효과로 해석하지 않습니다. 특히 합성 자료의 승인 문맥, 서비스 저하·정상 우회 경로, 특정 명령·프로세스가 정답과 강하게 연결되어 있습니다.

다음 학습 데이터에는 개별 로그와 집계량은 같고 호스트·ProcessGuid·시간 순서·연결 상대의 관계만 다른 정상/공격 쌍이 필요합니다. 합법적인 LSASS 접근, 승인된 관리 작업, 비슷한 스캔·인증 패턴도 정상 반례로 포함해야 합니다. 이 제안은 이번 제거 시험과 약한 라벨 규칙의 한계에서 도출한 개선안이며, 개선 후 성능 향상을 이미 측정했다는 의미는 아닙니다.

### 200ms는 낮은 부하의 판단 구간에서 달성했다

| 측정 구간 | p50 | p95 | p99 | 200ms 이내 |

실제 로그 리플레이의 첫 추론은 966.50ms였고 모델 로딩 시간은 별도입니다. 따라서 상주 모델과 사전 준비가 필요합니다. 초당 50건 시험에서 단일 작업자의 처리량은 약 30.64건/초로 입력률보다 낮아 대기열이 누적됐습니다. 40건짜리 초기 짧은 시험은 이 문제를 놓쳤고, 표에는 혼합 입력으로 늘린 시험을 사용했습니다. 원본 짧은 결과도 `runs/benchmark.json`에 보존했습니다. 20초 시험 통과가 장시간 안정성이나 더 긴 입력에서의 성능을 보장하지 않습니다.

두 지연 표본의 입력·초기화·시스템 상태가 다르므로 실제 로그 처리 p95가 warm 모델 표보다 작다는 것을 별도 최적화 효과로 해석하지 않습니다. 모델 서비스 측정은 토큰화·GPU 계산·결과 변환을 포함합니다. 실제 리플레이 측정은 판단을 수행한 이벤트의 상태 갱신·요약·모델·정책 검사를 포함하고 파일 전체 읽기/정렬, 센서 배출 지연, 네트워크 전달, 실제 장비 적용은 제외합니다. 앞선 로그의 상태 갱신이 실시간 입력률을 따라갈 수 있는지도 이 표만으로 입증되지 않습니다.

현재 단일 작업자 설계의 운용 범위를 정하려면 실제 입력 분포로 더 긴 부하 시험을 해야 합니다. 호스트별 중복 판단 병합, 입력 제한, 작은 배치, 작업자 분리 등은 다음 구현 후보이며 아직 이 모델에서 개선 효과를 측정하지 않았습니다. 근거는 `runs/sustained_load.json`, `runs/otrf_raw_decisions.jsonl`, `runs/results_summary.json`입니다.

### 실제 Zeek와 호스트 로그 처리 결과

시간이 맞는 OTRF 원시 자료에서 선택한 호스트 이벤트 78,455개와 Zeek 연결 613개를 처리했습니다. 상태 판단 935회 중 두 자료가 함께 존재한 것은 299회이고, 5-tuple·시간 일치가 있었던 것은 249회입니다. 최종 계획은 OBSERVE 490회, COLLECT_MORE 248회, HOST_ISOLATE 197회이며 **실제 실행은 0회**입니다. HOST_ISOLATE 197회가 참인 공격 197개 또는 성공적인 차단 197회를 뜻하지 않습니다. 동일 호스트·창의 반복 판단이고 해당 자료는 학습에 사용한 에뮬레이션입니다.

전역 버퍼 10,000개 상한 때문에 누적 31,625개 이벤트가 용량상 제거됐습니다. 이 사실을 기록하고 최종 실행기에서 증거 불완전으로 94개 판단을 보류했습니다. 공개 자료에 정상/공격별 정확한 창 단위 정답과 대응 결과가 없으므로 이 리플레이는 입력 파싱·관계 연결·방책 출력의 통합 시험으로만 해석합니다.

### 다음 학습과 유효성 입증 계획

1. **관계가 정답을 바꾸는 실제 자료 확보:** 동일 단일 로그만으로는 구분할 수 없는 정상/공격 쌍을 만들고, 호스트·사용자·프로세스·세션·시간 관계를 보존합니다. 캠페인·호스트·수집 날짜를 통째로 분리한 외부 test를 마련합니다. 공격군·정상 운영 작업별 표본 수를 사전에 정하며 운영 발생률을 유지한 시험도 별도로 둡니다.
2. **탐지와 방책 라벨을 분리:** ATT&CK는 시나리오와 증거의 기법 주석에 사용합니다. QoS·경로 전환·선택적 차단·격리의 정답은 mitigation 문구에서 바로 만들지 않고, 격리된 시험망에서 각 방책을 시행했을 때 공격 진행률·피해량·정상 서비스 비용으로 정합니다. 현재 약한 정책 교사는 초기 지도학습용으로만 사용합니다.
3. **이번 체크포인트를 출발점으로 재학습:** 관계를 바꾼 반례, 정상 관리 활동, 데이터 누락·지연을 늘립니다. threat/urgency/action의 학습 목표와 별도 보류 정책을 유지하되 비용 가중치는 관측한 피해와 오차단 비용으로 결정합니다. 보정 세트와 정책 선택 세트는 외부 test와 분리하고 모델·정책 버전을 함께 고정합니다.
4. **탐지 증분을 검증:** 동일 관측 시점에서 규칙, 수치 특징 분류기, 단일 관측원, 결합 모델을 비교합니다. 특히 단일 관측원에서 둘 다 실패하고 결합 시 성공하는 사례를 별도 집계합니다. 관계 순서/대상만 바꾼 시험, 승인 문맥 제거 시험, 새로운 공격군 제외 학습 시험으로 쉬운 패턴 의존을 확인합니다.
5. **제어 효과와 전체 지연을 검증:** 무대응·고정 정책·학습 정책을 동일 초기 상태에서 반복 비교합니다. 공격 확산 호스트 수, 유출량, 공격 성공률, 정상 연결 손실·지연, 복구 시간과 오차단률을 측정합니다. 첫 충분한 증거 생성 → 센서 전달 → 모델 결정 → 실제 규칙 적용 → 효과 관측에 각각 시각을 찍어 200ms 목표의 구간을 명시합니다. 지금 그 제어 시험을 하지 않았으므로 효과성 결론은 보류합니다.

실험 코드는 13개 파이프라인 검사, 저장 모델 재로딩, split/hash 검사, 동일 설정의 공식 런타임과 8개 사례 확률 일치 검사를 통과했습니다. 이것은 구현의 해당 경로가 검사됐다는 뜻이며 실환경 탐지 품질 인증은 아닙니다.

## 구현 구조

```text
Zeek conn JSON/TSV + Windows/Sysmon JSONL 또는 정규화 host JSONL
    → 관측 가능 시각 순으로 정렬 / 자산 식별자 통합 / 중복 제거
    → 300초 lookback / 동일 호스트 / 5-tuple + 흐름 시간 일치
    → 수치 요약 + 최근 중요 이벤트 4개 + 관계 특징 + 신뢰된 자산 문맥
    → Laya: threat(bool), urgency(0..2), response(6종)
    → 검증 세트에서 선택한 신뢰도 문턱 + 보호 자산/경로/식별 확인
    → OBSERVE / COLLECT_MORE / QOS_PROFILE / ROUTE_PROFILE / FLOW_DROP / HOST_ISOLATE
```

서로 다른 질문 3개를 배치 하나로 계산합니다. 모델이 원시 패킷마다 긴 설명을 생성하지 않습니다. 설명용 LLM 연결은 향후 별도 경로로 추가할 수 있으며 이 실험의 지연 측정에 포함하지 않았습니다.

`infer.py`는 파일을 읽는 재현 가능한 **오프라인 리플레이 실행기**입니다. `Correlator`와 `Predictor`는 지속 서비스에서도 재사용할 수 있지만 Kafka 소비자·실시간 HTTP 서비스·Security Router API 어댑터는 구현하지 않았습니다. FLOW_DROP은 방책 ID이며 실행할 5-tuple이나 패킷 필터를 완성한 규칙이 아닙니다. QoS/경로 프로파일도 이 실험의 추상 ID이므로 실제 장비 기능 목록에 매핑해야 합니다.

기본 리플레이는 호스트별 15초마다 판단합니다. 이는 측정용 샘플링 간격이고 200ms 반응 주기를 의미하지 않습니다. 실시간 구현에서는 도착 이벤트로 상태를 갱신하고 중요 이벤트의 조기 판단·호스트별 큐 제한을 별도로 구현해야 합니다. 300초는 과거 관측 범위이며, 판단을 위해 300초를 기다린다는 뜻은 아닙니다.

## 입력과 라벨

| 자료 | 사용 | 한계 |
|---|---|---|
| HF `bvsam/cic-ids-2017`, `traffic_labels` 8개 Parquet | 실제 공개 네트워크 흐름의 BENIGN/공격 라벨 | CICFlowMeter 형식. 네이티브 Zeek가 아니며 대응 방책 라벨은 설계자가 부여 |
| OTRF APT29 day1 Zeek + 역사 버전 Windows/Sysmon | 실제 두 관측원 연결, 정책 약한 라벨 학습 | 단일 공개 에뮬레이션; 공격 정답·방책 효과 정답으로 간주하지 않음. 전체 train 전용 |
| 생성한 독립 에피소드 1,800개 | QoS·우회·보류·격리 등 6종 정책 학습 | 합성 자료. 실제 공격 일반화 또는 피해 감소 증거가 아님 |

OTRF 현재 저장소의 5월 호스트 로그는 4월 Zeek 로그와 시간 범위가 맞지 않아 학습 결합에서 제외했습니다. 원본을 임의로 시간 이동하지 않고 시간대가 일치하는 역사 커밋의 호스트 로그를 사용했습니다. 날짜가 다른 로그도 원본 자료 보관 목적으로 다운로드되어 있습니다.

split은 `train/validation/calibration/policy_validation/test`로 분리합니다. 합성 자료는 에피소드 단위, CIC는 파일·출발지·30분 구간 단위로 분리하고 각 구간의 첫 5분을 사용합니다. 같은 데이터 수집 캠페인이 여러 split에 남으므로 새로운 캠페인에 대한 독립 검증은 아닙니다. 클래스별 상한 샘플링이 있어 운영 트래픽의 자연 발생률을 나타내지도 않습니다. 최종 test로 학습·온도 보정·정책 문턱을 선택하지 않습니다.

정책 문턱은 `policy_validation`에서 행동별 20개 이상, 관측 오류율 10% 이하인 후보를 사용합니다. 증거가 부족하면 문턱을 1.01로 설정해 보류합니다. 이는 통계적 오류율 보장이 아니며 표본 수·환경 이동의 제약이 있습니다. `infer.py`도 저장된 문턱을 적용하며 파일이 없으면 제한 조치를 보류합니다.

## 실행 재현

현재 서버에는 데이터, 의존성, 학습 완료 모델, 결과가 준비되어 있습니다. 다음 학습 명령은 결과를 덮어쓰므로 기존 실행을 보관한 뒤 사용하십시오. Python 3.11, NVIDIA GPU, CUDA 대응 드라이버와 `uv`를 사용합니다.

새 폴더에서 데이터를 재현할 때만:

```bash
uv venv --python 3.11 .venv
uv pip install --python .venv/bin/python huggingface_hub==0.36.0
export PATH="$PWD/.venv/bin:$PATH"
.venv/bin/python download_all.py
bash setup_remote.sh
.venv/bin/python build_dataset.py > dataset-build.log
```

`download_all.py`는 Hugging Face CLI와 고정 Git 커밋을 사용합니다. 전달받은 `vendor/laya`에 `.git`이 없는 경우 `--skip-runtime`으로 번들 소스를 사용합니다. 시스템에 `uv`가 없다면 먼저 해당 런타임을 준비해야 합니다. `setup_remote.sh`는 Torch 2.8.0 CUDA 12.8 및 Transformers 4.57.1을 설치하고 실제 패키지 목록을 `runs/requirements-resolved.txt`에 저장합니다. bit-for-bit 결과는 GPU 연산·라이브러리 버전에 따라 달라질 수 있습니다.

학습과 벤치마크:

```bash
cd /home/keinus/laya-security-lab
bash run_training.sh
bash run_benchmark.sh
bash run_extended_checks.sh
.venv/bin/python summarize_results.py
.venv/bin/python audit_artifacts.py
```

`run_training.sh`는 단위 검사, 입력 잘림/역전파 사전 검사, 3 에포크 학습, 별도 자료 온도 보정을 실행합니다. `run_benchmark.sh`는 원본/학습 모델 정확도·지연·짧은 부하 시험과 실제 원시 로그 리플레이를 순차 실행합니다. `run_extended_checks.sh`는 혼합 자료를 각 20초간 넣는 부하 시험과 공식 런타임 대비 입출력 일치 검사를 합니다. 병렬 GPU 작업은 지연 비교를 흐릴 수 있습니다. `runs/train.exit`, `runs/benchmark.exit`, `runs/extended.exit`의 0과 각 완료 JSON을 함께 확인하십시오. 정책 검사만 수정해 실제 로그를 다시 검증할 때는 `bash replay_raw.sh`를 사용할 수 있습니다.

실제 원시 로그 리플레이에서 10,000개 전역 버퍼 상한에 따른 관측 손실이 발견되어 최종 실행기는 누적 `buffer_dropped > 0`이면 COLLECT_MORE로 보류합니다. 현재 보류는 해당 프로세스가 다시 시작될 때까지 유지하는 보수적 동작입니다. 운영 전에 호스트별 상태 관리·창 내 손실 추적·입력량에 맞춘 용량 설계가 필요합니다. 상한 때문에 빠르게 계산된 결과를 완전한 증거에 대한 판단으로 해석해서는 안 됩니다.

실행 정밀도는 FP32 가중치와 BF16 autocast이며, 인코더 `reference_compile`은 저장된 None/자동 설정입니다. 공식 Agent의 eager 기본값 False와 다를 때 낮은 확신의 선택이 달라지는 사례를 발견했습니다. 일치 검사는 두 경로의 커널 설정을 같게 만든 뒤 확률까지 비교합니다. 기본 설정끼리의 차이는 `runs/upstream_parity_before_compile_match.json`, 원인 확인은 `runs/parity_debug.log`에 보존했습니다. `urgency`는 이 코드에서 최빈 클래스 0..2이고 공식 Agent의 실수 기대점수와 출력 의미가 다릅니다. 고정 소스 버전의 패키지 메타데이터에서 `backends`가 설치 누락되는 문제는 공식 비교 스크립트가 `vendor/laya` 전체 소스를 직접 로드하여 해결했습니다.

개별 로그 판단:

```bash
.venv/bin/python infer.py \
  --zeek /path/to/conn.log \
  --host /path/to/sysmon.jsonl \
  --assets assets.json \
  --model models/security-sft \
  --output runs/my_decisions.jsonl
```

`assets.json`은 이번 공개 실험망의 매핑입니다. 자신의 자산 매핑으로 교체해야 합니다. `replay_context.json`은 이번 공개 리플레이용으로만 신뢰된 식별자를 가정합니다. 운영에서는 승인 이력·자산 중요도·정상 우회 경로 등을 인증된 인벤토리에서 공급해야 하며 공격자가 보내는 로그 필드에서 승인 문맥을 읽어서는 안 됩니다. Windows/Sysmon 외의 Linux 로그는 직접 지원하는 원시 auditd 파서가 아니라 `Event` 스키마로 정규화한 JSON을 받습니다.

## 지연과 유효성 해석

관측 가능한 증거를 기다리는 시간 + 센서/수집 지연 + 상태 갱신/큐 + 모델 계산 + 정책 검사 + 장비 적용 시간 = 실제 대응 지연입니다. 여기서 벤치마크는 모델 또는 리플레이의 판단 구간을 측정합니다. 공개 conn.log에는 실제 센서 배출 시각이 없어 `ts + duration`을 사용한 하한 추정임을 기록합니다. 이미 종료된 연결 기록으로 과거 패킷을 차단할 수 없습니다.

5-tuple/시간 일치, 다른 포트 불일치, 미래 관측 차단, 중복 제거, 창 만료, 자산 경계, 보호 자산, split 분리를 검사했습니다. 다만 관계 특징은 현재 연결 횟수 요약이므로 특정 LSASS 접근 프로세스와 그 연결이 같은 ProcessGuid라는 인과 연결까지 입증하지 않습니다. 일상 보안 도구의 LSASS 접근, 합법 관리자 작업, NAT/재할당 IP, 지연 로그 및 새 공격군은 별도 검증이 필요합니다.

이 실험으로 판단할 수 있는 것은 해당 장비·입력에서의 계산 지연과 지정된 라벨에 대한 일치율입니다. 알려지지 않은 이상을 탐지하는 능력, 실제 공격 확산 방지, 정상 서비스 영향, 장비 적용까지 200ms 달성은 아직 입증하지 않았습니다.
