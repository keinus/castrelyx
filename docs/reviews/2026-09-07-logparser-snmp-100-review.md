## 수집 효율: 평균 건수보다 장애 시 지연이 문제

수집기는 장비별 OID들을 한 GET 요청에 넣고, 장비별 결과 하나를 이벤트로 생성한다. 매 OID마다 별도 요청을 보내는 구조는 아니다. 세션을 장비별로 재사용하고, 워커 수를 설정할 수 있다는 점은 장점이다.

| 항목 | 100대 × 20 OID × 60초 |
| --- | ---: |
| 논리 GET 요청, 정상 상태·재시도 제외 | 100회/분, 평균 약 1.67회/초 |
| Poll 결과 이벤트 | 100건/분, 144,000건/일 |
| 모두 수치인 경우 metric 저장 후보 | 2,000개/분, 약 33.3개/초, 2,880,000행/일 |
| 위 metric 30일 누적 | 86,400,000행 |

평균 요청량은 낮지만 실제 요청과 이벤트는 한 주기의 시작/완료에 몰릴 수 있다. v3 초기 엔진 발견·재동기화, 재시도, Trap/Inform, 다른 파이프라인 부하는 위 계산에서 제외했다. CPU·메모리·디스크 용량은 측정하지 않았다.

현재 기본값은 `intervalMs=60000`, `timeoutMs=5000`, `workerThreads=1`, `retries=0`, `queueSize=1000`이다. `invokeAll()`로 전체 장비 작업이 끝날 때까지 기다린 뒤 결과를 큐에 넣는다. 따라서 먼저 응답한 정상 장비의 결과도 느린 장비 때문에 늦게 전달된다.

아래는 정상 응답 50ms, 실패 요청은 timeout을 모두 소비한다고 가정한 계산이다. 실제 측정값이 아니다. 혼합 시나리오는 실패 장비 20대를 먼저 배치한 순서를 사용했다.

| 시나리오 | 워커 1개 | 워커 10개 | 워커 20개 |
| --- | ---: | ---: | ---: |
| 100대 정상 | 약 5초 | 약 0.5초 | 약 0.25초 |
| 20대 무응답, 80대 정상, timeout 5초·재시도 0 | 약 104초 | 약 10.4초 | 약 5.2초 |
| 100대 무응답, timeout 5초·재시도 0 | 약 500초 | 약 50초 | 약 25초 |
| 100대 무응답, timeout 5초·재시도 1 | 약 1,000초 | 약 100초 | 약 50초 |

전부 무응답인 단순 모델은 `ceil(장비 수 / 워커 수) × timeout × (retries + 1)`로 계산한다. 혼합 상태의 완료 시간은 장비 순서와 응답 분포에 따라 달라진다. SNMPv3 초기 교환, 이름 해석, OS 스케줄링 때문에 실제 값은 이 모델과 달라질 수 있다.

`nextPollAtMs`는 주기 시작 시 갱신되며, 주기가 길어지면 결과 큐를 비운 뒤 다음 주기를 곧바로 시작할 수 있다. 한 입력 안에서 주기가 중첩되지는 않지만, 60초라는 설정만으로 장비별 60초 수집이나 정상 장비의 신속한 전달을 보장하지 않는다. 장비별 스케줄과 완료 즉시 전달, 전체 동시 요청 제한이 필요하다.

## 우선 해결할 운영 제약

**1. 장비 상태를 직접 확인할 수 있어야 한다.** Overview의 `Inputs enabled`는 입력 설정 개수다. 입력 하나에 100개 targets를 넣어도 100대 중 몇 대가 성공했는지 보여주지 않는다. IP/장비명/그룹/수집 상태/최근 성공 시각/지연/연속 실패/마지막 오류를 한 표에서 검색·정렬·필터링할 수 있어야 한다. SNMP 응답 실패와 장비 전원 장애도 같은 상태로 단정하지 않아야 한다.

**2. 장비 등록과 변경 단위를 개선해야 한다.** targets 배열의 모든 필드를 펼치는 폼 대신 목록과 선택 장비 상세 편집을 분리하고, CSV·여러 줄 붙여넣기·중복 검사·등록 전 미리보기·일괄 인증 프로필 적용을 제공하는 편이 적합하다. 현재 대상 모델에는 대상별 enabled·그룹·개별 수집 주기·개별 OID 프로필이 없다. 입력 하나의 설정 수정은 해당 입력을 재시작하므로, 같은 입력에 묶인 장비들의 세션과 수집에 영향을 준다. 전체 파이프라인이 항상 재시작되는 것은 아니다.

**3. 실제 접속 검사가 필요하다.** 현재 Sample 테스트는 예제임을 명시하고 있어 과장된 성공 표시는 피하고 있다. 그러나 운영자는 저장/활성화 전에 대상 장비의 응답, 인증 실패, 지원하지 않는 OID, 부분 성공을 확인할 수 있어야 한다. 단건 `Test connection`과 다건 사전 검사, 실패 장비만 재검사가 필요하다.

**4. 포트·자원 자동 발견과 OID 요청 분할이 필요하다.** GETNEXT/GETBULK/WALK가 없으며, MIB 가져오기는 장비 검색이나 실제 인덱스 발견이 아니다. 장비마다 다른 ifIndex를 수동 관리해야 한다. 24포트 × 포트당 6항목 × 100대 × 60초면 metric 후보는 20,736,000행/일이고, 한 장비에 144개의 OID를 넣게 된다. 현재 요청에는 OID 수/응답 크기별 분할과 `tooBig` 후 축소 재시도가 없다. 실제 장비의 메시지 크기에 따라 실패·단편화가 발생할 수 있다. 크기 제약과 GETBULK 사용 시 단편화 고려는 [RFC 3416 §2.3](https://www.rfc-editor.org/rfc/rfc3416.html#section-2.3)에 명시되어 있다.

**5. 수집값을 관리 지표로 만드는 처리가 필요하다.** 누적 octet counter를 저장하는 것만으로 bps·사용률이 되지는 않는다. 실제 관측 시각 간 차분, 재부팅/카운터 초기화/불연속 확인, 64비트 정밀도 유지가 필요하다. `bps = 8 × Δoctets / Δseconds`, 사용률은 이를 링크 속도로 나눠 계산한다. 관련 counter와 discontinuity 의미는 [RFC 2863](https://datatracker.ietf.org/doc/html/rfc2863)에 근거한다. 현재 raw JSON은 Counter64를 문자열로 보존하지만 ClickHouse numeric metric은 Float64이므로 큰 정수의 정확한 차분은 이 컬럼만으로 보장할 수 없다. ifIndex·이름·방향·단위를 일관된 차원으로 저장하는 설계도 필요하다.

**6. 부분 실패와 알림의 운영 상태를 연결해야 한다.** 수집기는 `poll_status=partial`을 생성하지만 ClickHouse의 `snmp.poll.failure` 자동 생성은 `error`만 대상으로 한다. 따라서 일부 중요 OID가 빠져도 해당 자동 경고 이벤트가 만들어지지 않는다. 부분 실패, 값 없음, 오래된 데이터도 경고 조건으로 취급하고, 연속 실패 기준·복구·중복 억제·점검 시간 제외를 추가해야 한다. Trap/Inform은 기본 INFO로 저장되므로 장비별 의미와 심각도 규칙도 필요하다.

**7. 유실과 변경 영향을 관측할 수 있어야 한다.** poller는 모든 결과를 내부 큐에 넣은 뒤 읽기 시작한다. 큐 크기가 targets 수보다 작으면 한 주기의 뒤쪽 결과가 유실되며 현재는 경고 로그만 남는다. 기본 1,000은 100대의 이 문제를 피하지만, 작은 큐로 바꿨을 때를 검증하지 않는다. 드롭·timeout·부분 실패·큐 사용량을 입력/장비별 지표로 노출해야 한다. Inform 성공 응답은 메모리 큐 수락이며 최종 DB 저장 보장이 아니다. 유실을 허용할 수 없는 알림은 별도 영속 버퍼와 재처리 설계가 필요하다.

**8. Live Tail은 이력 화면을 대신하기 어렵다.** 브라우저에 최근 500개만 유지한다. SNMP poll만 100건/분이면 약 5분의 이벤트 수에 해당하며, 다른 로그와 알림이 섞이면 더 짧아진다. 장비별 시간 범위 조회와 장애 타임라인은 저장소를 조회하는 별도 화면이 필요하다.

## 현재 구현으로 시범 운영하는 경우

- 같은 OID 구성·인덱스·장비 유형을 공유하는 수집 그룹으로 입력을 나눈다. 100대를 무조건 단일 입력에 넣거나 반대로 무조건 입력 100개로 나누는 방식은 피한다. 예를 들어 20~25대씩 묶되 실제 장비 구성을 우선한다.
- 전체 동시 요청 10~20개를 초기 실험 범위로 삼는다. 단일 입력이면 워커 10~20, 25대짜리 입력 4개라면 각각 3~5부터 검증할 수 있다. 이는 측정 전 시작점이며 적정 성능을 보장하는 설정이 아니다.
- 60초 주기로 시작하고, timeout은 실제 응답 지연의 상위 구간과 WAN 여부를 보고 결정한다. LAN의 1~2초·재시도 1을 실험할 수 있지만 느린 장비에 일괄 적용하면 오탐이 생긴다. retries를 늘릴 때는 전체 장애 시 주기 완료 시간도 함께 계산한다.
- queueSize는 최소 해당 입력의 targets 수 이상으로 유지한다. 기본 1,000을 100대 운영에서 줄일 실익은 먼저 확인해야 한다.
- 포트 지표가 많으면 현재 GET 요청 한계부터 확인한다. 모델별 공통 OID와 실제 인덱스를 검증한 뒤 확대한다.
- 인증 상속과 실제 구현된 SNMPv3 환경변수 참조를 사용한다. Polling community에는 v3 passphrase와 동일한 env 참조가 있다고 가정하면 안 된다.
- ClickHouse metric·state·event와 raw 보관량을 따로 산정한다. 현재 자동 스키마 경로의 raw TTL은 7일, telemetry는 30일이다. 실제 저장소 설정, 압축률, 별도 원문/상태 행 때문에 행 수를 디스크 크기로 바로 변환할 수 없다.

## 개선 우선순위와 수용 기준 제안

| 우선순위 | 구현 범위 | 확인할 결과 |
| --- | --- | --- |
| P0 | 장비 상태 목록 + 실제 접속 테스트 | 100대 중 실패/부분 실패/오래된 데이터를 즉시 찾고, 실패 장비만 검사 가능 |
| P0 | 완료한 장비 즉시 전달 + 장비별 스케줄 + 지연/드롭 계측 | 20대 무응답 중에도 정상 장비 데이터가 실패 장비의 전체 종료를 기다리지 않음 |
| P0 | targets 일괄 등록·검색·그룹·검증 | 100대 등록과 인증 변경을 개별 카드 100개 편집 없이 수행 |
| P1 | OID 프로필·인덱스 발견·요청 분할 | 모델별/포트별 수집 구성을 재사용하고 메시지 크기 초과 시 복구 |
| P1 | rate 계산·정밀도·장비별 이력·알람 상태 | bps/사용률을 검증하고 경고 발생→확인→복구를 추적 |
| P2 | 변경 이력·선택 적용·역할별 작업 권한 | 운영자가 변경 대상과 영향 범위를 검토하고 필요한 권한으로 작업 |

운영 전에는 100대 정상, 20% 무응답, 100% 무응답, 일부 OID 불일치, v3 초기 연결, 출력 저장소 중단/복구, 활성 수집기 수정, Trap/Inform 집중 유입을 시험해야 한다. 제안하는 기준은 정상 장비 데이터의 나이 p95 90초 이하(60초 수집 기준), 정상 조건 24시간 무유실, 응답 없는 장비 존재 시 정상 장비 수집 유지, 알림 유실/중복 계수의 설명 가능성이다. 제안 기준은 실제 네트워크와 업무 요구에 맞춰 확정해야 한다.

## 실행한 검증

- `gradlew.bat test -PskipFrontend=true --offline`: 성공. 다만 모든 작업이 UP-TO-DATE여서 기존 결과를 재사용했다.
- `gradlew.bat test --rerun --tests '*Snmp*' -PskipFrontend=true --offline`: 새로 실행하여 성공. XML 기준 9개 테스트 클래스에서 선택된 33개 테스트, 실패/오류 0개. 실제 장비 100대 부하 시험은 아니다.
- 프런트엔드 전체 `npm test -- --reporter=dot`: 46개 중 45개 성공, Inform 샘플/파서 연결 테스트 1개가 5초 제한을 초과했다. 같은 테스트를 동일 기본 제한으로 단독 재실행하여 성공했다. 전체 테스트가 한 번에 모두 통과했다고 보고하지 않으며, 부하 의존 시간 초과 가능성은 남는다.
- 산술 모델로 워커별 폴링 완료 시간과 일별 이벤트/metric 개수를 계산했다. CPU·메모리·실제 네트워크·DB 저장 성능은 측정하지 않았다.
- 유효한 현재 화면 캡처를 확보하지 못했다. 시각적 사용성, 실제 사용자 작업 시간, 키보드/스크린리더 접근성은 미검증이다.
