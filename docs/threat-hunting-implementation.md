# 위협 헌팅 구현과 제품 출시 계획

현재 변경은 Manager의 헌팅 작업 공간, 서버 측 검색·집계, 실행 가능한 48개 시나리오, 조사·증거 저장, 규칙 관찰 운영을 구현한다. Linux auditd, Windows XML, Suricata EVE의 구조화 수집도 보강했다. 전체 제품 출시 계획 중 수집 정책 관리, 저장소 성능 최적화, 승인 기반 격리·복구, 실장비 검증은 후속 단계로 남아 있다. 현 상태를 운영 배포 완료로 간주하지 않는다.

## 분석가 작업 흐름

1. **탐색**에서 절대 시작·종료 시각, 관측 자산, 필드 조건을 지정한다. 최대 기간은 30일이며 페이지는 기본 200개, 최대 1,000개다. 화면에서 50·100·200·500·1,000개를 선택한다. 조건 편집기에서 중첩 AND·OR·NOT, 목록 포함/제외, 존재·CIDR·수치·문자열 조건을 편집한다. 요약·히스토그램·그룹 집계는 선택 기간 전체를 조회한다. 최근 10,000개를 먼저 가져온 뒤 필터링하지 않는다.
2. 시간 막대를 선택하면 해당 구간으로 다시 조회한다. 주소·계정·프로세스·파일 해시 등 이벤트 상세의 값을 다음 조건으로 사용한다. 조건을 편집한 뒤 아직 실행하지 않았으면 표·차트가 마지막 실행 기준임을 안내한다. 재조회가 완료되면 안내를 해제한다. 페이지 이동은 시각과 이벤트 ID를 함께 사용한다.
3. **헌팅 시나리오**에서 가설을 실행한다. 이벤트 결과 조건은 연관 이벤트를 지울 수 있으므로 시나리오 범위는 자산·주소·계정·원천 조건만 허용한다. 모든 항이 범위 필드인 AND·OR·NOT은 그대로 사용한다. 자유 검색어나 이벤트 유형·프로세스 등 범위 밖 조건이 있으면 전체 요청을 명시적으로 거부한다. 일부 항을 제거해 다른 의미의 가설을 실행하지 않는다.
4. **조사**에 가설, 메모, 진행 상태와 판정을 저장한다. 판정은 미판정·확인됨·반증됨·자료 부족이다. 이벤트 상세에서 조사로 증거를 고정하면 서버가 해당 조회 범위의 이벤트를 재검증하고 조회 조건·시점·자산 매핑·시나리오 문맥·SHA-256을 함께 저장한다. 열려 있는 조사의 증거·감사 목록도 갱신하며 저장하지 않은 분석 메모는 유지한다. 다른 조사로 이동한 뒤 도착한 이전 목록 응답은 표시하지 않는다.
5. **규칙·운영**에서 조직 룩업과 IOC를 관리하고, 규칙의 관찰 기록과 조사 후보를 확인한다. 조회 결과가 없을 때는 최근 실행 상태와 수집 가시성을 함께 확인한다.

시나리오의 `READY`는 선택 기간에 필수 필드 값이 존재하고 필요한 설정을 사용할 수 있다는 뜻이다. 센서의 연속 수집이나 탐지 정확도를 보장하는 상태가 아니다. 기준선 시나리오는 이전 14일 구간에 관측된 날짜가 14개 이상이어야 한다. 일별 최소 관측 검사를 통과해도 시간대별 공백은 별도 확인해야 한다.

기존 세션도 매 요청에서 현재 역할과 계정 활성 상태를 확인한다. 계정을 비활성화하면 기존 세션의 API 호출과 새 로그인을 거부한다. 세션은 살아 있지만 자료 권한이 없는 경우 403, 비활성 계정의 세션은 401로 구분한다.

`stored_at`은 새 Logparser 출력부터 기록된다. 기존 데이터는 `observed_at`을 대신 사용하므로 과거 시각으로 늦게 삽입한 기존 형식 이벤트까지 고정 시점에서 완전히 분리하지 못한다. 정규화 열 백필도 원천에 없던 저장 시각을 복원하지 않는다.

조건은 그룹과 NOT을 포함해 100개 노드·9단계, AND/OR 그룹당 30개 항, 목록당 100개 값까지 허용한다. 숫자는 유한한 값이어야 하며 숫자 필드의 문자열 포함/접두어 비교는 거부한다. 값이 없는 숫자는 수치·목록 비교에서 제외되므로 누락 조회는 `값 있음`의 부정을 사용한다. CIDR은 대역 하나씩 지정하며 원천 주소가 비어 있거나 IP 형식이 아니어도 전체 조회를 실패시키지 않고 해당 대역 일치에서 제외한다. `0.0.0.0/0`이나 `::/0`에서도 잘못된 주소를 포함하지 않는다. B04의 내부망 룩업도 같은 검사를 적용하는 2.1.1 정의이며 기존 관찰 기록을 새 정의의 승격에 사용하지 않는다.

편집 한도 경고는 해당 조건에만 표시한다. 다른 저장 검색을 복원하면 이전 경고를 초기화하며 같은 검색을 다시 선택해도 옛 경고를 되살리지 않는다.

### 조사 협업과 독립 검토

조사는 개인/조직 공유와 별개로 활성 OPERATOR·ADMIN을 담당자와 검토자로 지정한다. 지정은 개인 조사에 대한 해당 사용자의 접근을 허용하며, 회수·비활성화·VIEWER 전환 시 해당 권한이 사라진다. 조직 공유는 읽기 권한이며 다른 분석가의 공동 편집 권한이 아니다. 공유 범위와 담당자 지정은 소유자 또는 이미 접근 권한이 있는 관리자만 바꾼다. 접근할 수 없는 개인 조사를 관리자 역할만으로 열람하지 않는다.

허용된 비공개 전환·자신의 담당 해제는 저장 후 실행자의 접근 권한이 사라져도 완료한다. 저장 응답의 `casePermissions.read=false`로 권한 회수를 알리고, 화면은 해당 조사를 목록에서 제거하고 선택·근거·검토 편집창을 닫는다. 이후 해당 자료 조회는 거부한다. 다른 조사를 연 뒤 도착한 이전 저장 응답은 현재 선택과 미저장 초안을 교체하지 않는다.

분석 내용·판정 저장과 신규 증거 고정은 조사 버전을 증가시킨다. 기존 이벤트의 중복 고정은 버전을 올리지 않는다. 내용 저장·할당·검토 요청/판정·재개는 기대 버전을 검사하고, 같은 조사 행을 잠가 병행 요청에서 한 변경만 같은 버전을 사용할 수 있게 한다. 화면은 고정 결과의 직전 버전이 편집 중 기준과 같을 때만 그 고정으로 생긴 새 버전을 채택한다. 다른 변경은 미저장 메모를 유지한 채 충돌로 표시하며, 명시적인 최신 버전 불러오기는 미저장 내용을 교체한다.

검토 요청에는 담당자·독립 검토자, 저장된 가설/판정과 이유가 필요하다. 확인됨 판정에는 유효한 고정 근거가 필요하다. 검토자는 담당자·제출자·마지막 분석 작성자와 달라야 한다. 제출 시 제목·본문·공유 범위·조사 버전·유효 근거 ID/원본 해시/만료 시각 목록과 SHA-256을 고정한다. 검토 근거는 조사당 1,000개까지이며 더 많으면 조사를 나누도록 명시적으로 거부한다. 이 SHA-256은 서명이나 WORM 저장을 제공하지 않는다.

검토 중과 종료 후에는 내용·증거·할당을 변경하지 못한다. 지정 검토자는 이유를 기록해 승인/종료하거나 보완 요청으로 조사 중 상태로 돌린다. 근거가 만료돼 제출 manifest와 달라지면 승인은 거부하고 보완 요청은 허용한다. 소유자·접근 가능한 관리자는 이유를 기록해 검토 요청을 철회하거나 종료된 분석을 재개할 수 있다. 이전 요청의 ID/버전으로 새 판정을 재사용할 수 없다. 일반 저장 API로 검토/종료·할당 필드를 우회하지 못한다.

V9는 협업과 검토 기록을 추가하고 기존 조사에 소유자 기준 협업 행을 만든다. 기존 REVIEW/CLOSED 상태는 자동 승인으로 해석하지 않으며 이유를 기록해 분석을 재개한 뒤 새 절차를 따른다. 검토 목록은 20개씩 과거 방향으로 조회하고, 제출 snapshot은 선택한 기록에서 별도로 읽는다. 분석가 검색은 최대 100개와 초과 상태를 반환한다. 검토를 실행한 사용자·판정·이유·대상 버전과 이전/새 조사 버전은 감사 기록에 남는다. 기능별 시험 완료 여부는 시험결과 보고서에서 별도로 판정한다.

### 고정 증거와 완전한 내보내기

증거의 `snapshotJson`은 해시 대상 UTF-8 JSON 문자열이다. ADMIN에게는 저장한 원본 문자열과 `sha256`을, 다른 역할에는 원문 제거·마스킹 후 만든 문자열과 `exportSha256`을 제공한다. 원본 해시는 계속 구분해 보존한다. 큰 정수·소수·유니코드는 문자열 bytes로 검증하며, 파싱한 객체를 다른 언어에서 다시 직렬화한 값으로 원본 해시를 대신하지 않는다. 저장 문자열과 해시가 다르면 손상으로 명시적으로 거부한다.

JSON 내보내기는 동일한 조사 버전의 내용·담당/검토자·유효 고정 증거·보존된 전체 검토 snapshot·전체 감사 이력을 포함한다. 화면의 20개 검토/200개 감사 목록 한도로 자르지 않는다. 동일 조사 행 잠금과 DB snapshot 안에서 파일을 완성하고, 그 뒤에 파일 길이·SHA-256·완전성 manifest와 함께 전송한다. 일부 파일을 정상 응답으로 반환하지 않는다. 메모리에서 전체 이력을 조립하지 않고 순서대로 파일에 기록한다.

화면은 기대 조사 버전과 세션 CSRF로 준비 POST를 보낸 뒤, 사용자·역할에 묶인 15분 유효 일회성 HTTP 링크로 브라우저가 파일을 직접 받게 한다. 브라우저의 Blob으로 전체 파일을 복사하지 않는다. 다운로드 때 조사 접근 권한과 역할을 다시 확인하고, 역할/접근 회수·만료·링크 재사용을 거부한다. 다른 사용자의 거부된 시도는 원래 사용자의 링크를 소비하지 않는다. 기존 직접 GET 내보내기도 같은 완전성·권한 정책을 유지한다.

내보내기 준비는 동시에 2개, 기본 파일 한도는 256MiB(`manager.hunt.export-max-bytes`), DB/파일 준비 예산은 60초다. 초과·저장 장치 오류·손상은 전송 전에 거부하고 실패한 내보내기 감사 쓰기를 rollback한다. 준비 파일은 웹 경로 밖의 임시 파일이며 전송 완료/오류/미사용 만료 시 닫고 삭제한다. 프로세스가 종료돼도 OS의 close 시 삭제 옵션을 사용한다. 아직 전송하지 않은 파일은 15분 뒤 정리한다. 파일 해시는 서명이나 외부 위변조 방지를 의미하지 않는다.

고정 증거·작업은 만료 시각 이상에서 접근·정리 대상이며, 헌팅 감사는 생성 후 365일 이상에서 정리한다. 원천/조회 작업의 만료는 고정 사본을 지우지 않는다. 고정 사본 자체가 만료되면 원문은 열람/내보내기에서 제외하며 과거 검토의 ID·해시·만료 시각 참조는 유지한다. 만료 후 동일 원천을 새로 고정하면 현재 조회 범위를 다시 검증하고 새 증거 ID와 조사 버전을 만든다.

### 관계 분석과 복합 집계

관계 분석은 조회의 `includeRelations`로 요청하고 같은 작업·조건·고정 시점·자산 매핑에서 실행한다. 기능별 검증 상태는 시험결과 보고서에서 확인하며 전체 제품 완료와 구분한다. GUID는 원천 관측 자산·수집 경로·수집원·부팅/관측 영역 안에서만 연결한다. 숫자 PID는 부팅 ID와 명시적인 시작 시각이 함께 있어야 한다. 부모 GUID 참조만 있는 노드는 원천 이벤트 미관측으로 표시한다. 수명 역전·종료 후 실행·복수 부모·순환 참조는 관계 근거로 채택하지 않는다.

연결은 해당 이벤트의 5-tuple 또는 연결 ID를 근거로 표시한다. 센서·관측 영역이 다르거나 NAT로 tuple이 달라지면 별개다. Community ID만으로 센서 간 선을 만들지 않는다. 연결 ID를 재사용 가능한 session으로 합치려면 부팅 ID·명시적 연결 시작 시각·같은 tuple이 모두 필요하다. 그 외에는 동일 ID라도 이벤트별 관측을 유지한다. 프로세스의 통신 수행 관계는 `process.network`의 직접 식별 근거에만 표시한다.

그래프는 최대 10,000개 이벤트·1,000개 노드·2,000개 관계이며, 한도 초과·조회 중 원천 만료·필드 부족·참조 충돌은 불완전 상태로 표시한다. 노드/관계별 대표 근거는 20개를 보존한다. 근거 열람은 `/queries/{job}/events/{event}`에서 작업 소유자·시점·원래 조건을 다시 검사하고 역할별 마스킹을 적용한다. 첫 페이지에 없는 이벤트도 이 경로로 열람할 수 있다.

관계 정의 `relations-1.0.1`은 연결 식별 필드가 빠진 통신 이벤트와 고립된 프로세스 노드의 시작·수명 충돌도 불완전 상태에 반영한다. 관계 선이 없어도 데이터 품질 상태를 완전으로 올리지 않는다.

화면의 프로세스 계층 목록과 선택 노드의 방향 관계도는 같은 모델을 사용한다. React가 SVG와 상호작용을 소유하며, 선택 노드를 중심으로 앞·뒤 12개씩 고정된 세 열에 배치한다. 전체 관계와 근거는 목록에서 확인한다. 무작위 배치를 사용하지 않고 확대되지 않은 글자를 유지하며, 모바일에서는 계층/근거 목록을 먼저 제공하고 관계도는 내부 스크롤로 펼친다. 검색·유형·노드 선택은 해당 작업의 일시 상태이며 새 작업에서는 초기화한다. SVG 방향선은 관계 존재·방향만 표현하고 위험도를 표현하지 않는다. 이 레이어는 node-link 스킬을 읽고 로컬에서 별도 설계/검토한다.

복합 집계는 `groupFields` 1~3개를 지원한다. 전체 일치 이벤트에서 이벤트 수·고유 관측 자산·송신/수신 바이트를 함께 계산하고 선택한 측정값으로 정렬한다. 101번째 조합은 표시 한도 초과 감지에 사용하고 상위 100개를 반환한다. 누락값을 유지하며 조합 포함은 AND, 조합 제외는 해당 AND 전체의 NOT이다. 값이 있는 조합의 각 항은 EXISTS와 동등 비교를 함께 검사해 SQL NULL이 부정 결과를 바꾸지 않게 한다. 예를 들어 443 포트 조합을 제외해도 포트가 없는 다른 이벤트는 유지한다. 누락값 조합 자체를 선택하면 NOT EXISTS로 비교한다. 기존 `groupBy` 한 필드 저장 검색도 유지한다. 추가 집계 필드와 관계 분석 선택은 저장 검색에 함께 복원된다.

### 물리 조회 모델의 배포

관리자의 **규칙·운영 → 헌팅 저장소**에서 정규화 열을 설치하고 일별 파티션을 선택해 백필한다. 조회나 Manager 시작만으로 운영 저장소를 변경하지 않는다. 기존 `manager_events`의 7개 입력 열은 유지하며 `hunt2_` 접두어의 MATERIALIZED 열을 추가한다. 추출식은 JSON 조회와 같은 필드 레지스트리에서 생성하고 열별 형식·정의 지문을 검사한다. 기존 열의 정의가 다르면 자동으로 덮어쓰지 않는다.

열이 없거나 정의가 다르거나 메타데이터를 읽을 수 없으면 JSON 조회를 유지한다. 호환되는 열이 모두 있으면 탐색·시나리오·증거 조회가 물리 열을 사용한다. 기존 파트는 백필 전에도 같은 식으로 값을 계산하며, 백필은 저장된 값을 만들어 반복 추출 비용을 줄인다. 결과 ID와 시점·별칭 계약은 유지한다. ClickHouse의 [MATERIALIZE COLUMN](https://clickhouse.com/docs/reference/statements/alter/column#materialize-column)을 사용하며, 수집 원문을 다시 입력하지 않아 이벤트를 추가하지 않는다.

백필은 한 일자씩 비동기 mutation으로 제출한다. 다른 미완료 mutation이 있으면 새 백필을 거부한다. 화면에는 전체 진행 중 변경 수와 최근 정규화 변경 100개, 남은 파트와 오류를 표시한다. 요청 접수와 실제 완료를 구분하고 완료는 ClickHouse 상태로 확인한다. Manager가 종료되어도 이미 접수된 mutation은 저장소가 계속 처리한다. 백필의 추가 디스크·I/O를 고려해 한 파티션부터 진행한다. 정상화 열 조회를 되돌릴 때는 `MANAGER_HUNT_PHYSICAL_READ_ENABLED=false`로 Manager를 재시작한다. 원문이나 정규화 열을 삭제할 필요가 없다.

관리 API는 `/api/security/hunt/v2/storage`의 GET 상태, POST `/install`, POST `/backfill`이며 모두 ADMIN만 접근한다. POST는 기존 세션 CSRF 검증을 적용하고 요청·접수 감사 기록을 남긴다. DB 계정에는 메타데이터 SELECT와 대상 테이블의 ADD/MATERIALIZE COLUMN 권한이 필요하다. 전체 JSON 검색은 원문을 읽으므로 물리 열 설치 후에도 같은 비용 감소를 기대할 수 없다. 30일·100EPS 성능은 별도 부하 시험 대상이다.

관리자 외 사용자에게 내려주는 증거는 권한에 따라 원문이 제외된 사본이다. `sha256`은 고정 원본의 해시이고 `exportSha256`은 내려준 사본의 해시다. 이 해시는 서명·외부 타임스탬프·WORM 저장을 제공하지 않는다.

조회·시나리오·취소 응답, 저장 검색의 목록/상세/저장 응답과 증거 안의 조회 메타데이터에도 같은 역할별 마스킹을 적용한다. 자유 검색어와 중첩 조건의 명령 인수/메시지 값으로 원문을 우회해 노출하지 않는다. 가려진 조건은 `redacted`로 표시하고 화면에서 재실행을 막아, 마스킹 문자열을 원래 조건처럼 실행하지 않는다. 저장한 원래 조건과 관리자 조회는 보존한다.

저장 검색에서 `text`·`groupBy` 등 선택값을 생략하거나 null로 보내도 같은 마스킹과 재실행 차단을 적용한다. 공개 필드만 사용하는 최소 조건은 정상 복원한다. OPERATOR의 알려진 비밀 패턴은 password/passwd/token/secret/api_key/api-key 할당과 Authorization의 인용 값·Bearer/Basic 인증값을 포함한다. 키의 대소문자·인용 부호, 공백/탭, 인용 값 안의 이스케이프를 처리하고 뒤따르는 공개 인수는 유지한다. 적용 대상은 명령 인수·메시지와 이들 필드의 중첩 조건·자유 검색어이며 임의의 문자열 전체를 비밀로 분류하는 기능을 의미하지 않는다.

### 승인 예외 요청과 적용

시나리오 후보에서 제목·변경 근거·적용 시작/종료를 작성해 예외를 요청한다. 서버는 요청자가 소유한 유효한 완료 작업의 실제 후보만 사용한다. 시나리오 버전·모든 그룹 식별자·형식 있는 원천 조건·관측자 매핑·정책 버전에 묶으며, 클라이언트가 보내는 임의 범위/승인 상태로 대체하지 않는다. 대상 식별자가 불명확한 후보는 예외로 만들지 않는다. 계정 영역의 누락값은 별도의 정확한 값이며 wildcard가 아니다.

- 요청자와 다른 ADMIN이 검토·승인하거나 반려한다. 요청자·관리자는 요청/승인을 이유와 함께 철회할 수 있다. VIEWER는 변경하지 않는다. 승인 전·반려·승인 전 취소 자료는 요청자/관리자만 읽고, 승인된 예외와 그 철회 이력은 조직에 공유한다. 버전 충돌과 자기 승인을 거부하고 승인 원문은 수정하지 않는다. 갱신은 억제된 원본 후보에서 새 요청·새 승인을 만든다.
- 적용 기간은 현재 전후 30일 이내에서 최대 30일이며 밀리초 정밀도를 사용한다. 시작은 포함하고 종료는 포함하지 않는다. 미래 적용 기간도 요청할 수 있으며 기존 후보는 범위의 근거 예시다. 해당 기간에 전체 관측 구간이 들어오는 후보만 억제하고 일부만 겹치거나 엔터티·원천 조건·매핑·정책 버전이 다른 후보는 유지한다.
- 작업 생성 시 당시 유효한 승인 사본을 고정한다. 만료·철회는 새 실행부터 반영하며 이전 작업의 결과/승인 문맥은 바꾸지 않는다. 원래 후보는 `suppressed`에 승인 ID·버전·기한·근거 해시와 함께 남긴다. 빈 결과·미수집·불완전 결과와 예외 억제를 구분한다.
- 작업의 완료 결과와 `HUNT_EXCEPTION_APPLIED` 감사를 같은 DB 트랜잭션에 저장한다. 취소된 작업은 적용 감사를 남기지 않고, 감사 실패는 성공 결과까지 되돌린다. 같은 완료 처리의 재시도·동시 실행은 중복 감사를 만들지 않는다. 검토 이력과 실제 적용 이력은 별도로 열람·페이지 이동한다.
- 요청 당시의 정확한 UTF-8 `evidenceJson`과 SHA-256을 보존한다. 비관리자는 역할에 따라 가려진 문자열과 별도 `exportEvidenceSha256`을 받고 원본 해시는 구분한다. 작업/원천의 만료가 요청 근거를 삭제하지 않는다. 사용자별 유효 대기 요청 50개는 사용자 행 잠금으로 제한하고, 한 실행 범위의 유효 승인 사본은 500개 한도로 명시적으로 거부한다.

이 흐름은 승인 예외에 한정된다. 개별 finding의 오탐 피드백·알림 억제/해제, 피드·규칙 버전 배포와 전체 M4 운영 인수는 별도 남은 요구사항이며 이 기능으로 대체하지 않는다.

### Episode 연결과 실행별 근거

같은 규칙 버전·그룹 식별자의 후보는 시나리오 윈도 이내에서 연결되는 모든 episode를 병합한다. 연결 구간을 확장해 더 이상 연결되는 episode가 없을 때까지 검사하며, 밀리초 정밀도의 경계는 포함한다. 떨어진 구간·다른 그룹·다른 규칙 버전은 유지한다. 연결된 대표 후보가 500개를 넘으면 일부만 병합하지 않고 해당 완료 처리를 명시적으로 실패시킨다.

후보 생성 SQL도 서로 떨어진 구간을 먼저 분리한다. 집계·주기성 시나리오는 조건을 만족한 각 관측 창을 시각·이벤트 ID 순서로 정렬하고, 이전 창의 최대 끝과 현재 창의 시작 사이가 시나리오 윈도를 초과할 때 새 episode를 시작한다. 같은 시각의 서로 다른 이벤트도 하나의 올바른 구간에 속해야 한다. 연관 시나리오는 기존의 개별 연결 구간을 유지한다. 정의는 2.2.0으로 기록하며, 이전 정의 문맥·예외를 재해석하지 않는다. 기존 규칙은 정의 변경 시 재관찰 절차를 따른다.

- 대표 ID는 기존 후보 중 최초 관측 시각·ID 순서로 정한다. 병합 전 후보는 삭제하지 않고 `merged_into`와 `MERGED` 상태로 대표를 가리킨다. 추가 병합 시 조회용 연결은 대표까지 평탄화하고 원래 병합 경로·직전 DB 행의 정확한 문자열·해시는 별도 이력에 보존한다.
- 각 실행의 원래 후보·조건·시점 문맥을 별도 문자열과 SHA-256으로 저장한다. 같은 작업/동일 후보의 재처리는 사본이나 알림을 중복 생성하지 않는다. 서로 다른 실행이 같은 episode를 확인해도 실행별 사본은 유지한다. V11 이전 후보는 남아 있는 마지막 결과만 `LEGACY_LAST_RESULT`로 보존하며 사라진 과거 실행 전체를 복구했다고 표시하지 않는다.
- 병합 후에는 대표 알림 하나만 유지한다. 다른 알림은 `MERGED`로 보존하고 기존 확인/해결 API로 다시 활성화하지 못하게 한다. 여러 알림이 병합되면 ACTIVE, ACKNOWLEDGED, RESOLVED 순서로 주의가 필요한 상태를 유지한다. 관찰 실행은 알림을 새로 만들지 않는다.
- 후보·알림·실행 사본·병합 이력·감사는 규칙 완료와 같은 트랜잭션에 속한다. 연결 알림 누락·근거 저장·감사 실패는 부분 갱신을 남기지 않는다. 같은 규칙 runtime 잠금으로 완료 처리와 중복 실행을 직렬화한다.
- 현재 접근 가능한 규칙의 후보만 상세와 각 페이지를 열람할 수 있다. 비공개 자료는 다른 ADMIN에게도 공개하지 않는다. 실행 사본과 병합 이력은 각각 20개씩 과거 방향으로 조회하고 매번 접근권한과 해시를 확인한다. 비관리자의 병합 사본은 내부 직렬화 payload를 먼저 파싱해 보호 필드를 가린 후 별도 문자열/해시로 제공한다.
- 규칙·운영의 실행·병합 근거 화면은 요청할 때 로드한다. 원래 후보, 대표 ID, 정확한 서버 문자열과 원본/권한 사본 해시, 이전 버전 자료의 한계를 구분한다. 선택·역할 변경은 이전 응답과 캐시를 제거하고, 페이지 오류와 재조회는 명시적으로 표시한다.

이는 TH-M4-03의 중복 episode 부분 구현이다. 오탐 피드백·개별 알림의 시간 제한 억제/해제와 전체 운영 인수는 계속 구현·시험 대상으로 유지한다.

운영 룩업은 이름별 한 개이며 조직 공유다. `trusted_scanners`·`approved_dns`는 IP, `internal_networks`는 CIDR, `approved_services`는 포트 번호, `business_hours`는 Asia/Seoul 기준 `9-18`, `trusted_processes`는 실행 경로, `protected_paths`는 경로 접두어다. IOC는 IP·도메인·SHA-256·TLS 지문을 지원하며 출처, 0~100 신뢰도와 만료 시각이 필요하다. 만료·사용 해제 IOC는 새 작업에 포함하지 않는다. 이미 실행한 작업에는 당시 값이 남는다. 외부 피드 자동 동기화는 아직 제공하지 않는다.

규칙은 초안 → 관찰 운영 → 활성, 또는 관찰·활성 → 일시 중지로 전환한다. 활성화는 관리자만 가능하며 서버가 7일 관찰 기간과 `READY`, 결과 완전성을 충족한 완료 10회 이상을 검사한다. 관찰 중에는 조사 후보만 기록하고, 활성화 후 기존 알림 시스템에 연결한다. 겹치는 시간대의 동일 연관 키는 후보·알림을 병합한다. 운영 중 본문 수정은 일시 중지 후 새 초안으로 수행하며 다시 관찰해야 한다. 단일 Manager 인스턴스를 전제로 하고, 반복 실행에는 대화형 분석을 위해 작업 하나만 배정한다. 60초 주기보다 실행이 밀릴 수 있으므로 최근 실행 시각을 확인한다.

현재 E05의 호스트·계정 수준 연관은 프로세스가 해당 전송을 직접 수행했다는 근거가 아니다. G04·F06 등은 서비스 ID·파일 경로 등 동일 연관 키가 양쪽 이벤트에 실제 존재해야 한다. 원천에 없는 키를 추측해 연결하지 않는다. DNS 답변 배열과 등록 도메인별 하위 이름 분석은 보강했으며, Linux 실행과 네트워크의 동일 프로세스 연결은 추가 구현 대상이다. ATT&CK 기술별 커버리지와 실제 탐지 성능도 별도 평가한다. 분류 기준은 [MITRE Enterprise Techniques](https://attack.mitre.org/techniques/enterprise/)를 참고한다.

## 수집 배포

기존 Agent와 Logparser를 함께 갱신한다. 수신 프레임 테이블의 기존 7일 TTL, canonical 이벤트의 기존 30일 TTL은 유지한다. canonical JSON에 들어간 원문 필드 분리, 설정 가능한 보존 정책, 180일 집계는 후속 작업이다.

- **Windows:** Security·System·PowerShell과 함께 Sysmon Operational·TaskScheduler Operational 채널을 조회한다. `ToXml()`의 이름 있는 EventData를 보존하고 메시지 표시 길이와 독립적으로 명령 인수·GUID·해시를 전달한다. Sysmon 설치와 감사 정책 활성화는 관리자가 별도로 수행한다. 현재 PowerShell 증분 RecordId 방식이며 네이티브 EvtSubscribe/bookmark는 후속 구현이다.
- **Linux:** `/var/log/audit/audit.log`가 존재하고 읽기 권한이 있을 때 수집한다. SYSCALL·EXECVE·PATH·PROCTITLE을 audit ID로 묶고 EOE 이후 실행 이벤트를 만든다. 부분 레코드는 cursor와 함께 저장하며 30초 지연·크기 초과에는 `audit.incomplete`를 출력한다. auditd 설치·규칙 활성화는 자동으로 수행하지 않는다. 파일 변경·읽기 이벤트 분류에는 `castrelyx_persistence`, `castrelyx_credentials` 감사 키가 필요하다.
- **Suricata:** EVE JSON 중첩 프로토콜 정보와 64비트 flow ID, Community ID를 보존한다. flow ID는 연결 ID이며 개별 이벤트 ID로 사용하지 않는다. 송수신 바이트는 toserver/toclient 방향이므로 관측 위치·내부망·NAT 맥락을 확인한다.
- **Logparser:** canonical 이벤트에 `event_uid`, `stored_at`, `normalization_version=security-2.0`을 추가한다. 기존 입력→parser→transform→structured→output 경계와 ACK 동작은 변경하지 않는다.

## 설치와 검증

기존 배포 절차로 Manager 프런트엔드와 Java 백엔드를 함께 빌드한다. Java만 시험할 때의 `-PskipFrontend=true`는 새 화면 배포 빌드를 대신하지 않는다. Flyway V6~V9는 헌팅 자료, 규칙 실행 상태, 자산·시나리오 문맥, 조사 협업·검토 이력을 추가한다. 운영 MariaDB를 백업하고 동일 버전의 복원 사본에서 먼저 migration을 확인한다. ClickHouse 서버 시간대는 기존 canonical 쓰기와 일치하는 UTC로 운영한다.

```powershell
cd manager/frontend
npm ci
npm test -- --run
npm run build
cd ..
.\gradlew.bat test -PskipFrontend=true
.\gradlew.bat bootJar
```

격리 ClickHouse 통합 테스트는 `HUNT_TEST_CLICKHOUSE_URL`을 지정해 실행한다. 현재 테스트 계정은 코드에 명시된 로컬 fixture 전용 `huntqa`이며 운영 계정을 사용하지 않는다. 테스트마다 `hunt_test_<UUID>` DB를 만들고 그 DB만 제거한다. MariaDB 11.4·ClickHouse 24.8 격리 인스턴스에서 V6~V8 migration과 실제 API의 10,050건 집계·최신 10,000건 이전 검색·cursor·증거 저장·관찰 승격 제한·CSRF를 확인했다.

2026-10-22 TH-R005 전체 자동 회귀 결과는 Manager 423개·Logparser 525개·프런트엔드 41개·Linux Agent 240개 통과다. Windows 네이티브 Agent는 239개 통과·symlink 생성 권한 부재로 1개 건너뜀이며 프런트엔드와 Windows Agent 빌드가 성공했다. 업데이터 시험의 Windows 전용 기대값을 OS 계약에 맞게 정정하고 양 OS에서 다시 실행했다. 이후 Chrome에 연결해 실제 조회·설치·백필·조사 증거 흐름을 시험했다. 화면 캡처는 Chrome CDP 시간 초과로 보류되어 DOM·동작 증거와 시각 검증을 구분한다. 최신 물리 조회 모델 변경과 회차별 결과는 [시험결과 보고서](threat-hunting-test-report.md)에 별도로 기록한다.

검증에는 10,050건 뒤의 이벤트 검색, 동일 시각 cursor 페이지, Windows 코드 중복 구분, 재전송 중복 제거, 지연 삽입 제외, 자산 별칭의 원본 ID 유지, 48개 SQL 실행, 인증 연관·주기성·신규 대상·SID 연관의 정상/의심 사례, CSRF·개인 자료 접근·증거 재검증·규칙 활성화 우회 방지가 포함된다. 48개 정상화 의미 변형과 JSON/물리 열의 실제 승인 DB·적용 감사 시험을 추가했다. 시험 통과/미실행 범위는 결과 보고서에서 확인하며, 원천 수집 전수·장시간 부하·Windows VM·Router 복구 검증은 남아 있다.
