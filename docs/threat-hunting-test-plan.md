# 위협 헌팅 제품 시험 계획서

## 목적과 판정

[구현 계획](threat-hunting-implementation.md)의 전체 기능을 제품 수준으로 구현하고, 동일한 시험 절차로 그 동작을 입증한다. 기존 단위 시험 통과나 48개 SQL의 문법 실행만으로 제품 적합을 판정하지 않는다. 이 계획과 요구사항 ID는 구현 상황에 맞춰 축소하지 않는다. 미구현·미시험·환경 제약은 합격이 아니다.

시험 판정은 PASS(기대 결과와 증거 일치), FAIL(기대 결과 위반), BLOCKED(명시한 외부 환경·장비 부재), NOT_RUN(아직 미실행), NOT_IMPLEMENTED(기능 미완성)로 기록한다. 전체 제품 판정 PASS는 아래 모든 요구사항의 시험이 PASS이고 필수 건너뜀이 0건인 경우에만 가능하다. 과거 시험은 참고 증거이며 현재 변경의 재시험을 대신하지 않는다.

실패가 있으면 해당 회차의 보고서·입력·로그·코드 해시를 보존한다. 구현과 입력 계약을 검토해 원인을 수정하고, 새 회차를 생성하여 **환경 준비와 데이터 초기화부터 전체 시험을 다시 시작**한다. 디버깅 중 선택 시험을 사용할 수 있으나 선택 시험만 통과한 회차를 최종 합격 회차로 사용하지 않는다. 의도적으로 오류를 주입하는 시험은 올바른 거부·복구가 관측되면 PASS다.

## 환경과 안전한 초기화

- 대상은 별도 MariaDB·ClickHouse, 격리 Linux·Windows 시험 호스트, 시험용 Router, Chrome이다. 운영 DB·운영 NIC·사용자의 관리 경로에는 격리나 장애 주입을 실행하지 않는다.
- ClickHouse 의미 시험은 회차 전용 `hunt_acceptance_<UUID>` DB만 생성·초기화·제거한다. 각 사례의 데이터와 룩업을 새로 넣으며 이전 사례의 기준선이나 결과를 재사용하지 않는다. 운영 계정은 사용하지 않는다.
- Manager의 헌팅 컨트롤러·규칙 통합 시험은 각각 별도 H2 DB를 사용한다. 캐시된 다른 앱 context의 주기 작업이 mock 저장소용 작업이나 규칙 fixture를 실행하지 못하게 분리한다.
- 전체 프런트엔드 시험은 jsdom worker를 최대 4개로 제한해, 실행 중인 QA 서비스와 시험 환경이 과도하게 경합하지 않도록 한다. 모든 시험과 기존 5초 제한을 유지한다. 실제 QA 서버는 다시 컴파일하는 디렉터리와 분리한 고정 클래스/리소스 복사본으로 시작하고 해당 해시를 보존한다.
- 앱 자동화와 localhost 화면 확인은 Chrome만 사용한다. 연결 부재는 UI 시험의 BLOCKED이며 내장 브라우저로 대체하지 않는다. 서버·수집기·문서 작업은 계속한다.
- 실제 공격 도구는 실행하지 않는다. 실행·자격 증명·유출 사례의 정상화된 기록과 승인된 무해한 수집 fixture를 사용한다. 대응 시험은 독립 관리 경로와 복구 콘솔이 있는 전용 VM/NIC에서 수행한다.
- 환경별 OS·CPU·메모리·버전·시간대·앱 revision과 dirty diff SHA-256·fixture SHA-256·명령·시작/종료 시각·종료 코드·JUnit/Go/브라우저 증거를 회차 폴더에 기록한다. 쓰기 지연과 재전송은 관측 시각과 저장 시각을 따로 지정한다.

## 회차 절차와 산출물

승인 예외의 세부 시험은 TH-M0-02의 APPROVED 변형과 TH-M4-03의 일부다. TH-M4-03의 오탐 피드백·알림 억제/해제·episode 병합 전체 기준을 유지하며 승인 예외만으로 해당 요구사항을 합격 처리하지 않는다.

Episode 부분은 분리된 두 후보를 연결하는 입력, 연결 확장을 반복해야 하는 이전 자료, 윈도와 동일/1밀리초 초과 경계, 다른 그룹/규칙 버전, 같은 작업 재처리·동시 완료를 시험한다. 대표 후보 1개와 활성 알림 1개, 병합 전 ID/원문·실행별 사본·감사를 독립 대조한다. 20개 초과 실행/병합 페이지, 비공개 전환 후 각 역할의 접근 회수, 내부 직렬화 payload의 비밀값 마스킹·원본/권한 사본 해시, 사본 손상 거부, 연결 알림 누락·감사 오류의 전체 rollback, 500개 초과 연결의 명시적 실패도 포함한다. V11 이전의 마지막 결과 사본을 실제 전체 실행 이력과 구분한다. 선택 단위/MockMvc 시험 뒤 실제 MariaDB·규칙 실행·Chrome과 전체 회귀를 새 환경에서 다시 수행한다.

- 실제 소유 작업·READY/완전 결과·후보 인덱스 검사, 원천 조건/관측자 매핑/시나리오·정책 버전과 모든 엔터티 식별자 고정. 임의 범위/상태 위조·일반 저장 경로 수정·다른 사용자 작업·만료 작업 거부.
- ADMIN 독립 승인·반려, 요청자/관리자 철회, VIEWER 변경 차단. 요청/반려/승인 전 취소의 개인 경계, 승인 후 공유, 잘못된 CSRF 4종, 비인증 접근, 동시 승인·버전 충돌·대기 요청 한도의 경합을 검증한다.
- 시작 직전/동일·종료 직전/동일/직후, 미래 적용·부분 구간·다른 엔터티/원천/매핑·정의/정책 버전에서 잘못된 억제가 없어야 한다. 원문 손상 거부, 원본과 권한 사본의 정확한 문자열 해시, 원천/작업과 독립적인 요청 근거 보존을 검증한다.
- 완료 결과와 적용 감사의 원자성·취소·실패 rollback·중복 완료 및 검토/적용 이력의 50/20건 초과 페이지를 확인한다. 갱신은 새 요청/승인이고 과거 실행 사본은 보존되어야 한다.
- Chrome에서 후보 요청→다른 관리자 검토/승인→새 실행 억제와 원본 열람→철회→새 후보 평가, VIEWER 열람·1440×900/390×844·키보드·오류 초안·늦은 응답·권한 변경 시 이전 검토 내용 제거를 확인한다.

TH-M2-06의 마스킹 경계에는 1KB·4KB·32KB·64KB 인용 값과 인용 부호 이스케이프를 포함한다. 긴 정상 원천 값을 처리하면서 stack overflow·원문 누출이 없어야 하며, 뒤따르는 공개 인수와 ADMIN 원본은 유지해야 한다.
