# CastrelSign

CastrelSign은 서비스와 에이전트의 **인증서를 발급하고, 인증서·업데이트 서명에 사용하는 키를 관리하는 서버**입니다. 웹 화면에서는 운영자에게 인증서를 요청하거나, 발급 상태를 확인하고, 공개 인증서를 내려받을 수 있습니다.

## 처음 사용하는 분을 위한 요약

**일반 사용자는 `내 서비스 → 인증서 요청 → 내 요청 → 인증서 다운로드` 순서만 먼저 익히면 됩니다.** 키 교체, 삭제, HSM 설정은 키 운영 담당자의 업무입니다.

| 내가 하려는 일 | 시작할 화면 | 완료 여부를 확인하는 방법 |
|---|---|---|
| 처음 로그인하기 | [접속과 로그인](#manual-login) | 오른쪽 위에 내 계정이 표시됨 |
| 내 서비스의 인증서 확인 | [내 서비스](#manual-user-services) | 서비스와 인증서 만료일 확인 |
| 새 인증서 발급·갱신 | [인증서 요청](#manual-user-enroll) | `내 요청`에 요청 번호가 생김 → 운영자 승인 후 다운로드 |
| 발급된 인증서 설치 | [연결 가이드](#manual-user-guide) | 서비스에 적용한 뒤 실제 연결을 확인 |
| 관리자로 서비스 등록 | [애플리케이션 관리](#manual-admin-services) | 목록에 서비스가 표시됨; 사용자 할당은 별도로 설정 |
| 사용자 인증서 요청 승인 | [인증서 요청 검토](#manual-admin-reviews) | 요청 상태가 `승인 완료`로 바뀜 |
| 에이전트 최초 등록 | [에이전트·등록 토큰](#manual-admin-agents) | 에이전트가 등록을 마친 뒤 목록과 인증서에 표시됨 |
| 키 교체 또는 권한 변경 | [키 관리](#manual-admin-keys), [교체 순서](#manual-rotation) | 다른 보안 담당자의 승인과 최종 상태 확인 |
| 오류나 작업 이력 확인 | [감사 기록](#manual-admin-audit), [문제 해결](#manual-troubleshooting) | 요청 ID·작업 결과·운영 상태 확인 |

## 1. 접속과 로그인

### 1.1 준비할 것

운영자에게 **서버 주소, 접속 구분, 본인에게 발급된 인증 토큰**을 받습니다. 일반 사용자는 담당할 서비스도 할당받아야 합니다. 운영 환경의 변경 담당자는 개인별 MFA 인증 앱도 준비합니다.

| 항목 | 의미 | 예시·주의할 점 |
|---|---|---|
| 서버 주소 | CastrelSign 웹 화면 주소 | 운영: `https://서버주소:8443/console/` |
| 접속 구분 | 어느 계정 체계로 로그인할지 선택 | `관리자` 또는 `일반 사용자` |
| 인증 토큰 | 운영자가 전달한 개인별 로그인 비밀 문자열 | 계정 이름, 인증서, 6자리 MFA 코드와 다름 |
| 서비스 식별자 | 담당 서비스의 고유한 이름 | `preview-api`; CSR의 CN에도 같은 값을 사용 |
| MFA 코드 | 인증 앱에서 잠시 유효한 6자리 숫자 | 운영 관리자 변경 작업 시 입력 |

현재 로컬 검증 서버 주소는 [로컬 관리 콘솔](http://127.0.0.1:8444/console/)입니다. 이 주소는 **서버를 실행한 같은 PC에서만** 사용할 수 있습니다. 로컬 검증용 HTTP 주소와 운영용 HTTPS 주소를 구분하세요. 서버가 종료되어 있으면 브라우저에 이전 화면이 남아 있어도 로그인할 수 없습니다.

### 1.2 로그인 순서

![로그인 화면 — 접속 구분과 인증 토큰 입력](docs/screenshots/console/01-login.png)

1. 브라우저에서 운영자가 알려 준 `/console/` 주소를 엽니다.
2. **접속 구분**에서 본인 토큰의 종류에 맞게 선택합니다. 인증서를 요청하는 서비스 담당자는 `일반 사용자`입니다.
3. **인증 토큰**에 전달받은 **원문**을 붙여 넣습니다. `Bearer ` 접두사, 따옴표, 앞뒤 공백은 넣지 않습니다. 정책 파일에 적힌 SHA-256 해시를 입력하는 것도 아닙니다.
4. **로그인**을 누릅니다.
5. 일반 사용자는 `내 서비스`, 조회 권한이 있는 관리자는 `키 관리`로 진입합니다. 일부 관리자 역할은 `서비스·에이전트`로 진입합니다.
6. 오른쪽 위 계정 이름을 눌러 역할과 접근 범위가 맞는지 확인합니다.

**로그인 토큰은 어디에서 받나요?** 웹 화면에는 회원 가입이나 비밀번호 찾기 기능이 없습니다. 관리자는 외부 관리자 정책에 등록된 개인 토큰을, 일반 사용자는 외부 사용자 정책에 등록된 개인 토큰을 운영자에게 받습니다. 개발 호환 계정은 서버 시작 시 설정한 `CASTRELSIGN_ADMIN_TOKEN`을 사용합니다. `legacy-admin`은 표시 이름이지 로그인 토큰이 아닙니다. 모든 설치에서 통하는 기본 비밀번호나 공통 토큰은 없습니다.

**자동 로그아웃:** 세션은 유휴 15분 또는 최대 8시간이 지나면 만료됩니다. 다시 로그인하면 됩니다. 토큰 원문은 브라우저의 localStorage/sessionStorage에 저장하지 않습니다. 역할이나 서비스 할당을 운영자가 회수하면 기존 세션에도 다음 요청부터 반영됩니다.

**로그아웃:** 관리자는 왼쪽 메뉴 맨 아래 **로그아웃**, 일반 사용자는 오른쪽 위 계정 이름 → **로그아웃**을 사용합니다. 창이 작으면 메뉴나 페이지 안을 아래로 스크롤하세요.

## 2. 용어와 공통 조작법

### 2.1 헷갈리기 쉬운 용어

| 용어 | 쉬운 설명 | 사용자가 할 일 |
|---|---|---|
| 개인키 (`client.key`) | 서비스가 자기 신원을 증명할 때 쓰는 비밀 파일 | 서비스 호스트에서 만들고 그곳에 보호 보관. 웹에 업로드하지 않음 |
| 공개키 | 개인키에 대응하는 공개 가능한 정보 | CSR과 인증서에 포함됨 |
| CSR (`client.csr`) | “이 공개키로 이 서비스의 인증서를 발급해 주세요”라는 서명된 신청서 | 서비스 환경에서 만들고 인증서 요청에 제출 |
| 인증서 (`.pem`) | 서비스 이름과 공개키를 CA가 서명한 공개 증명서 | 승인 후 다운로드하여 해당 개인키와 함께 서비스에 설치 |
| CA | 인증서에 서명하는 발급자 | 관리자가 CA 키와 신뢰 자료를 운영 |
| 신뢰 번들 | 상대방의 인증서·서명을 검증할 때 신뢰할 공개 인증서·키 묶음 | 운영자와 지문을 확인하고 검증하는 프로그램에 설치 |
| 인증 토큰 | 사람이 웹 콘솔에 로그인할 때 쓰는 비밀 문자열 | 로그인 화면에서만 해당 계정의 토큰 입력 |
| 등록 토큰 | Agent 또는 Application의 최초 등록에 쓰는 제한된 비밀 문자열 | 대상 프로그램의 등록 설정에 전달. 웹 로그인에 사용하지 않음 |
| MFA / TOTP | 인증 앱이 생성하는 짧은 유효기간의 6자리 코드 | 운영 관리자가 변경 확인 창에서 입력 |
| 키 별칭 / 버전 | 용도별 키 이름과 교체 세대 | `ca-root v1`, `ca-root v2`처럼 이름이 같아도 버전이 다름 |
| 의존성 | 아직 그 키가 필요한 인증서·TLS·릴리스·백업 기록 | 삭제 전에 남아 있는 참조를 확인 |
| 승인 요청 | 중요한 **KMS 키 변경**을 다른 보안 담당자가 승인하는 절차 | 활성화·권한·삭제 등의 요청을 확인 |
| 인증서 요청 검토 | 일반 사용자의 **CSR 발급 요청**을 운영자가 검토하는 절차 | 서비스와 요청자를 확인하고 발급 승인 또는 반려 |

### 2.2 화면 읽는 방법

- **상단 환경·테넌트:** 접속한 서버의 환경과 관리 범위입니다. 예시 화면의 `local-validation · castrelyx`를 운영 환경 이름으로 착각하지 마세요.
- **관리자 왼쪽 메뉴 / 사용자 상단 메뉴:** 역할에 맞는 화면만 표시됩니다. 창 폭이 좁으면 **메뉴 열기** 버튼을 이용합니다.
- **오른쪽 위 계정 이름:** 내 계정과 권한을 확인합니다. 메뉴가 없거나 버튼이 비활성화되면 먼저 이곳을 확인합니다.
- **목록의 이름 또는 오른쪽 화살표:** 해당 항목을 선택합니다. 상세 정보는 화면 오른쪽이나 목록 아래에 나타납니다.
- **새로고침:** 서버에서 정보를 다시 읽습니다. 운영자가 승인한 뒤에는 눌러서 결과를 확인하세요.
- **검색:** 현재 불러온 목록에서 검색합니다. 검색어가 남아 있으면 항목이 숨겨질 수 있습니다. 검색어 지우기 버튼으로 초기화할 수 있습니다.
- **표시할 항목이 없습니다:** 오류 안내가 없다면 조회된 항목이 없다는 뜻입니다. 신규 설치, 미등록 서비스, 할당 부족, 검색 조건을 확인합니다.
- **긴 화면·입력 창:** 페이지 또는 대화상자 안을 스크롤하면 하단 버튼이 나옵니다. 아래 캡처에는 긴 페이지의 전체 내용도 담았습니다.

### 2.3 관리 작업의 공통 확인 창

관리 작업은 버튼을 누른 뒤 대상과 입력값을 확인하는 창이 열립니다. 값을 입력하고, 필요한 경우 **MFA 코드**를 입력한 뒤 **작업의 대상과 영향을 확인했습니다.**를 체크하고 **확인 후 실행**을 누릅니다. **취소** 또는 닫기 버튼은 실행 전 입력 창을 닫습니다.

운영 관리자에게 MFA가 요구되면 **현재 인증 앱의 새 코드**를 사용합니다. 같은 관리자가 동일한 30초 코드를 연속 변경 작업에 재사용할 수 없습니다. 다음 코드가 나온 뒤 진행하세요. 예시 `legacy-admin`은 개발 호환 계정이라 캡처에 MFA 입력이 보이지 않습니다.

작업 후에는 창이 닫히거나 결과가 표시되고 목록이 갱신됩니다. **키 변경 요청의 접수 성공은 실제 변경 완료와 다릅니다.** `승인 요청`에서 다른 담당자의 승인을 마친 뒤 최종 키 상태를 확인해야 합니다. 반면 서비스 차단이나 릴리스 활성화 등의 작업은 확인 후 실행 시 실제로 적용됩니다.

## 3. 일반 사용자 화면별 사용법

일반 사용자 포털은 **Application 서비스 인증서**를 위한 화면입니다. Agent 최초 등록은 [관리자의 등록 토큰 절차](#manual-admin-agents)를 사용합니다.

**첫 인증서 발급의 전체 순서**

1. 운영자가 서비스를 등록하고 내 계정에 할당합니다.
2. `내 서비스`에 담당 서비스가 보이는지 확인합니다.
3. 서비스 호스트에서 개인키와 CSR을 만듭니다.
4. `인증서 요청`에서 CSR을 제출합니다.
5. `내 요청`에서 승인 상태를 확인합니다.
6. 공개 인증서를 다운로드합니다.
7. 인증서·개인키·CA 신뢰 번들을 서비스에 적용하고 실제 연결을 확인합니다.

<a id="manual-user-services"></a>

### 3.1 내 서비스 — 내가 관리할 서비스 확인

![내 서비스 — 인증서가 있는 서비스와 없는 서비스](docs/screenshots/console/40-user-services.png)

**언제 사용하나요?** 로그인 직후 담당 서비스, 인증서 유무, 만료일을 확인할 때 사용합니다.

1. 상단 **내 서비스**를 엽니다.
2. 목록에서 서비스 이름을 누릅니다. 검색창에 식별자나 표시 이름을 입력해 찾을 수도 있습니다.
3. 상세 영역에서 서비스 식별자, 인증서 만료일, 업무 권한을 확인합니다.
4. 인증서가 없으면 **인증서 요청**, 이미 발급 이력이 있으면 **갱신 요청**을 누릅니다.
5. 발급된 인증서가 있으면 **공개 인증서 다운로드**로 PEM 파일을 받습니다. 진행 상황은 **요청 이력 보기**로 확인합니다.

| 상태 | 의미 | 다음 행동 |
|---|---|---|
| 인증서 없음 | 아직 해당 서비스의 인증서가 없음 | CSR 준비 후 요청 |
| 연결 가능 | 서버가 인증서·서비스·CA 상태를 유효하다고 판단 | 서비스에 인증서를 적용하고 실제 연결 확인 |
| 만료 임박 | 화면 기준 7일 이내 만료 예정 | 교체 일정을 잡고 갱신 요청 |
| 만료됨 / 사용 불가 | 현재 인증에 사용할 수 없는 상태 | 인증서 화면에서 재확인하고 운영자에게 문의 |
| 차단됨 | 관리자가 서비스 사용을 차단함 | 운영자에게 차단 사유 확인 |

**`연결 가능`은 서비스 호스트의 접속 시험을 통과했다는 뜻은 아닙니다.** 다운로드한 파일을 적용하고 연결을 시험하는 일은 서비스 담당자가 수행합니다. 서비스가 하나도 보이지 않으면 운영자에게 **내 계정 ID와 필요한 서비스 ID**를 전달하여 할당을 요청하세요.

<a id="manual-user-enroll"></a>

### 3.2 인증서 요청 — CSR 제출부터 접수까지

**준비물:** 사용할 서비스 ID, 해당 서비스 환경에서 생성한 EC P-256 개인키와 CSR. 아래 예시는 서비스 ID가 `preview-api`일 때입니다. OpenSSL이 설치된 서비스 호스트의 **새 작업 디렉터리**에서 실행하세요. 기존에 사용 중인 `client.key`를 덮어쓰지 않습니다.

```sh
openssl ecparam -name prime256v1 -genkey -noout -out client.key
openssl req -new -key client.key -out client.csr -subj "/CN=preview-api"
openssl req -in client.csr -noout -subject -verify
```

`preview-api`를 실제 서비스 식별자로 바꿉니다. 화면의 `app:preview-api`는 유형을 붙인 표시이므로 **CN에는 `preview-api`만** 씁니다. `client.key`는 서비스에 남겨 두고 담당 계정만 읽을 수 있게 합니다. 업로드할 파일은 **`client.csr`**입니다.

**1단계: CSR 등록**

![인증서 요청 — 서비스 선택과 CSR 입력](docs/screenshots/console/42-user-enroll.png)

1. `내 서비스`에서 대상을 선택한 후 **인증서 요청 / 갱신 요청**을 누릅니다. `내 요청 → 새 인증서 요청`으로도 진입할 수 있습니다.
2. **서비스**가 의도한 대상인지 확인합니다. 차단된 서비스는 선택 목록에서 제외됩니다.
3. **CSR 파일**에서 `.csr` 또는 `.pem` 파일을 선택합니다. 또는 파일 전체 내용을 **CSR 내용**에 붙여 넣습니다.
4. 내용에 `-----BEGIN CERTIFICATE REQUEST-----`부터 끝줄까지 포함됐는지 확인합니다.
5. **다음: 내용 확인**을 누릅니다. 이 단계에서는 아직 서버에 발급 요청을 접수하지 않습니다.

| 검사 항목 | 요구 조건 |
|---|---|
| 크기 | 최대 64 KiB |
| 공개키 알고리즘 | EC P-256 (`prime256v1`) |
| CN | 선택한 서비스 식별자와 정확히 일치 |
| CSR 서명 | 서버에서 유효성 검사 통과 필요 |
| 개인키 | 제출 금지; `PRIVATE KEY`가 포함된 입력 거부 |
| 중복 대기 | 한 서비스에 승인 대기 요청 1개 |
| 요청 횟수 | 사용자당 최근 24시간 내 접수 20건 제한 |

**2단계: 내용 확인**

![인증서 요청 — 접수 직전 내용 확인](docs/screenshots/console/43-user-enroll-review.png)

1. 서비스 이름과 CSR 크기를 확인합니다. 이 화면으로 넘어왔다고 해서 서버의 서명·CN 검사가 끝난 것은 아닙니다.
2. 수정할 내용이 있으면 **이전**을 누릅니다.
3. 맞으면 **인증서 요청 보내기**를 누릅니다. 서버가 현재 서비스 권한과 CSR을 검사하여 접수합니다.
4. 성공하면 **요청을 등록했습니다**와 요청 ID가 표시됩니다. **내 요청 보기**로 이동하여 기록을 확인합니다.
5. 운영자가 검토할 때까지 기다립니다. 요청을 보낸 것만으로 인증서가 발급되거나 서비스에 설치되지는 않습니다.

**갱신할 때:** 새 개인키를 생성했다면 새 인증서는 반드시 그 개인키와 함께 설치해야 합니다. 승인 시 기존 인증서는 이전 버전으로 전환되므로 운영자와 적용 시점을 맞추세요. 요청을 반복해서 제출하기 전에 `내 요청`에 대기 중인 항목이 있는지 확인합니다.

<a id="manual-user-requests"></a>

### 3.3 내 요청 — 처리 상태와 사유 확인

![내 요청 — 요청 번호와 처리 상태](docs/screenshots/console/44-user-requests.png)

1. 상단 **내 요청**을 엽니다.
2. 요청 번호·서비스·등록 시각·상태를 확인합니다. 최근 200건을 표시합니다.
3. 요청 번호나 오른쪽 화살표를 눌러 상세를 엽니다.
4. 처리일과 검토 사유를 확인합니다. 운영자가 방금 처리했다면 **새로고침**을 누릅니다.
5. `승인 완료`일 때 상세의 **공개 인증서 다운로드**를 누릅니다. 반려된 경우 사유를 수정하여 새 요청을 만듭니다.

![내 요청 상세 — 승인된 요청의 검토 사유와 다운로드](docs/screenshots/console/45-user-request-detail.png)

| 상태 | 설명 |
|---|---|
| 승인 대기 | 접수됐으며 운영자의 검토가 필요함 |
| 승인 완료 | 발급이 완료된 요청. 공개 인증서를 받을 수 있음 |
| 거절됨 | 검토에서 반려됨. 상세 사유를 확인하고 수정 후 새 요청 |

요청 상태의 `승인 완료`는 **과거 발급 처리 결과**입니다. 지금도 그 인증서가 유효한지는 `인증서` 화면에서 다시 확인합니다. 상세의 진행 표시 역시 서비스에 파일이 설치되었다는 확인은 아닙니다.

<a id="manual-user-certificates"></a>

### 3.4 인증서 — 발급 파일 받기와 현재 상태 확인

![내 인증서 — 공개 인증서와 현재 상태 확인](docs/screenshots/console/41-user-certificates.png)

1. 상단 **인증서**를 엽니다. 화면 제목은 `내 인증서`입니다.
2. 서비스명 또는 일련번호로 검색하고 원하는 항목을 선택합니다.
3. 상세의 **Subject**, 일련번호, 발급일, 만료일을 확인합니다. `Subject`의 CN이 담당 서비스와 맞아야 합니다.
4. **현재 상태 다시 확인**을 누르면 서버에서 유효기간·서비스 상태·CA 신뢰 상태를 다시 조회합니다.
5. **공개 인증서 다운로드**를 누릅니다. 파일 이름은 `서비스명-일련번호.pem` 형식입니다.
6. 받은 공개 인증서와 CSR을 만들 때 사용한 개인키를 함께 서비스에 적용합니다.

이 화면에서 받는 파일에는 개인키가 없습니다. 개인키를 잃어버렸다면 다운로드로 복원할 수 없습니다. 새 개인키와 CSR을 생성하여 재발급을 요청해야 합니다. 만료·차단·폐기된 인증서는 파일이 존재하더라도 정상 연결에 사용할 수 없습니다.

<a id="manual-user-guide"></a>

### 3.5 연결 가이드 — 파일을 실제 서비스에 적용

![연결 가이드 — CSR 명령과 공개 신뢰 자료 다운로드](docs/screenshots/console/46-user-guide.png)

**언제 사용하나요?** CSR 작성 방법을 보거나 인증서를 받은 뒤 서비스에 적용할 때 사용합니다.

1. 상단 **연결 가이드**를 엽니다.
2. 첫 발급이면 화면의 OpenSSL 명령에서 서비스 식별자를 바꿔 CSR을 준비합니다.
3. 운영자에게 대상 CA 또는 업데이트 검증 키의 지문을 별도 경로로 확인합니다.
4. 인증서 검증에 필요한 **CA 신뢰 번들 → 다운로드**를 누릅니다. 파일은 `ca-trust-bundle.pem`입니다.
5. 업데이트 서명을 검증하는 프로그램을 구성할 때만 **업데이트 검증 키 → 다운로드**를 사용합니다. 파일은 `update-trust-bundle.pem`입니다.
6. 서비스의 TLS 설정에 **개인키, 발급된 인증서, 신뢰할 CA 번들**을 연결하고 해당 프로그램의 reload 또는 재시작 절차를 수행합니다.
7. 실제 mTLS 연결, 서비스 식별자, 만료일을 확인합니다. 구체적인 설치 경로와 설정 항목은 서비스를 실행하는 프로그램의 문서를 따릅니다.

| 파일 | 만드는 곳·받는 곳 | 쓰는 곳 |
|---|---|---|
| `client.key` | 서비스 호스트에서 생성 | 자신의 신원 증명; 비밀 보관 |
| `client.csr` | 서비스 호스트에서 생성 | CastrelSign 발급 요청에 제출 |
| `서비스명-일련번호.pem` | 승인 후 인증서 화면에서 다운로드 | 자신의 인증서로 설정 |
| `ca-trust-bundle.pem` | 연결 가이드에서 다운로드 | 상대 인증서의 발급자를 검증 |
| `update-trust-bundle.pem` | 연결 가이드에서 다운로드 | 업데이트 파일 서명 검증 |

공개 인증서를 받는 것과 서비스에 설치하는 것은 별도 작업입니다. 콘솔은 서비스 호스트에 파일을 자동 배포하거나 재시작하지 않습니다. 일반 사용자에게도 CA 번들은 제공하지만 CA 개인키는 제공하지 않습니다.

### 3.6 사용 이력 — 내가 담당하는 서비스의 작업 기록

![사용 이력 — 요청·승인·다운로드 기록](docs/screenshots/console/47-user-activity.png)

1. 페이지 오른쪽 위 **사용 이력**을 누릅니다. 좁은 화면에서는 메뉴에서도 찾을 수 있습니다.
2. 순번·시각·서비스·작업을 확인합니다. 내 계정에 기록된 최근 200건 중 현재 접근할 수 있는 서비스의 기록을 표시합니다.
3. 검색창에 서비스 이름이나 작업명을 입력합니다.
4. 순번 또는 화살표를 눌러 상세 요청 ID 등을 확인합니다. **상세 닫기**로 접습니다.
5. **내보내기**를 누르면 현재 검색 결과를 `service-activity.csv`로 내려받습니다.

| 작업명 | 의미 |
|---|---|
| `CSR_REQUESTED` | CSR 요청 접수 |
| `CSR_APPROVED` | 운영자가 승인하여 인증서 발급 |
| `CSR_REJECTED` | 운영자가 반려 |
| `CERTIFICATE_DOWNLOADED` | 공개 인증서 다운로드 |

내 사용 이력은 전체 서버의 관리자 감사 로그와 범위가 다릅니다. 다른 서비스까지 포함한 문제는 운영자에게 문의하세요.

## 4. 관리자 화면별 사용법

### 4.1 역할부터 확인하기

![관리자 내 계정 — 역할과 키 범위](docs/screenshots/console/37-admin-account.png)

오른쪽 위 계정 이름을 누르면 **내 계정**이 열립니다. 관리자라고 해서 모든 작업을 수행할 수 있는 것은 아닙니다.

| 역할 | 담당 작업 |
|---|---|
| `AUDITOR` | 키·승인·감사·운영 상태·설정 조회. 지정된 키 범위 적용 |
| `KEY_ADMIN` | 키 새 버전 준비, 변경 요청, 긴급 중지 등의 키 관리 |
| `SECURITY_OFFICER` | 다른 개인이 요청한 KMS 변경 승인 |
| `OPERATOR` | 서비스·에이전트·등록 토큰·릴리스·사용자 CSR 검토 |
| `VERIFIER` | 인증서의 현재 인증 가능 여부 검증 |

키 변경·승인 담당자가 콘솔에서 조회도 하려면 해당 키 범위와 필요한 조회 역할을 함께 받아야 합니다. 예시의 `legacy-admin`은 `SECURITY_OFFICER` 역할이 없으므로 **혼자서 2인 승인을 완료할 수 없습니다.** 실제 요청자·승인자는 개인별 계정으로 구성합니다.

**처음 운영하는 경우:** `서비스·에이전트`에서 서비스 등록 → 외부 사용자 정책에 담당자 할당 → 담당자가 CSR 제출 → `인증서 요청 검토`에서 승인 → 사용자 다운로드·적용 → 상태와 이력 확인 순서로 진행합니다.

<a id="manual-admin-services"></a>

### 4.2 서비스·에이전트 → 애플리케이션

![애플리케이션 목록 — 서비스 등록·권한·차단](docs/screenshots/console/17-admin-services.png)

**목적:** 인증서를 발급받을 Application 서비스를 등록하고 업무 권한·차단 상태를 관리합니다. 변경에는 `OPERATOR`가 필요합니다.

**서비스 등록**

1. 왼쪽 **서비스·에이전트** → **애플리케이션** 탭을 엽니다.
2. **서비스 등록**을 누릅니다.
3. **서비스 식별자**에 고유한 ID를 입력합니다. 예: `payment-api`. 이후 사용자 정책과 CSR CN에 같은 값을 사용합니다.
4. **표시 이름**에 사람이 알아보기 쉬운 이름을 입력합니다. 예: `결제 API`.
5. 공통 확인 절차를 마치고 **확인 후 실행**을 누릅니다.
6. 목록에서 새 서비스가 보이는지 확인합니다. 이때는 서비스만 등록된 것이며 인증서가 발급된 것은 아닙니다.

![애플리케이션 등록 입력 창](docs/screenshots/console/18-admin-service-dialog.png)

**사용자에게 서비스 할당**

서비스 등록만으로 일반 사용자의 `내 서비스`에 나타나지 않습니다. 서버 운영자가 `CASTRELSIGN_PORTAL_USERS_FILE`에 지정한 외부 JSON 파일의 해당 사용자 `services` 목록에 ID를 추가해야 합니다. 웹에는 사용자 정책 파일 편집 기능이 없습니다. 예시 형식은 다음과 같습니다.

```json
[
  {
    "id": "payment-owner",
    "tokenSha256": "<개인별 로그인 토큰의 SHA-256 소문자 64자리 hex>",
    "services": ["payment-api"]
  }
]
```

위 해시 자리표시자는 실제 사용값이 아닙니다. 운영자는 안전하게 생성한 로그인 토큰 원문을 해당 사용자에게 전달하고 정책에는 해시를 기록합니다. 기존 파일을 수정할 때 다른 사용자 항목도 유지합니다. 파일 경로를 처음 설정할 때는 서버 구성·재시작 절차가 필요하며, 이미 지정된 파일의 계정·범위 변경은 다음 요청부터 재검사됩니다. 형식과 설치는 [콘솔 설치 안내](frontend/README.md)를 참고하세요.

**권한·차단 관리**

- 행의 **권한**을 누르면 업무 권한 문자열을 추가합니다. 사용할 권한 이름은 연동 API가 요구하는 값으로 지정합니다. 이 권한은 사용자의 서비스 할당이나 KMS 키의 `SIGN` 권한과 다릅니다.
- **차단**은 해당 서비스의 기존 인증서와 미사용 등록 토큰을 회수합니다. 대상과 영향을 확인한 후 실행합니다.
- 차단 해제는 행에 표시되는 재활성화 동작을 사용합니다. **재활성화만으로 기존 인증서가 복구되지 않으므로 새 등록·발급이 필요합니다.**

<a id="manual-admin-reviews"></a>

### 4.3 인증서 요청 검토 — 일반 사용자 발급 요청 처리

![인증서 요청 검토 — 기존 승인 기록과 검토 사유](docs/screenshots/console/36-admin-reviews.png)

1. 왼쪽 **인증서 요청 검토**를 엽니다. `승인 요청` 메뉴와 구분하세요.
2. 목록에서 서비스와 요청자를 확인하고 항목을 선택합니다.
3. 상세의 요청 ID·접수일·현재 상태를 확인합니다. 이전 처리 기록이면 처리일·검토자·사유도 표시됩니다.
4. 대기 요청의 서비스 담당자와 발급·갱신 목적을 확인합니다. 갱신이라면 인증서 적용 시점도 맞춥니다.
5. 적절한 요청이면 **승인 및 발급**, 수정이 필요하면 **거절**을 누릅니다. 대기 상태이고 `OPERATOR` 권한이 있어야 처리할 수 있습니다.
6. 확인 창에 **작업 사유**를 구체적으로 적고 필요한 MFA를 입력한 뒤 실행합니다. 사유 예: `payment-api 담당자 확인, 갱신 배포 일정 확인 완료`.
7. 목록의 상태가 `승인 완료` 또는 `거절됨`으로 바뀌었는지 확인합니다. 사용자는 `내 요청`에서 결과와 사유를 확인할 수 있습니다.

승인 직전에 서버가 사용자 서비스 접근 권한, 서비스 차단 여부, CSR 서명 등을 다시 검사합니다. 인증서 발급 시 기존 인증서는 이전 버전으로 전환됩니다. **이 화면의 승인은 실제 발급 작업**이며, KMS 키 변경의 2인 승인 대기열을 만드는 버튼이 아닙니다. 이미 처리된 요청에는 처리 버튼이 나타나지 않습니다. 캡처는 기존에 승인된 검증 요청입니다.

<a id="manual-admin-certificates"></a>

### 4.4 인증서 — 전체 발급 대상 확인

![관리자 인증서 — 서비스·에이전트 인증서 조회](docs/screenshots/console/16-admin-certificates.png)

1. 왼쪽 **인증서**를 엽니다. Application과 Agent 인증서를 함께 조회합니다.
2. 검색으로 발급 대상이나 일련번호를 찾고 행을 선택합니다.
3. 유형, Subject, 일련번호, 발급일·만료일을 확인합니다.
4. **현재 상태 확인**으로 지금 인증에 사용할 수 있는지 검사합니다. 이 동작에는 `VERIFIER` 역할이 필요합니다.
5. 공개 파일이 필요하면 **공개 인증서 다운로드**를 사용합니다.

목록의 발급 기록과 현재 인증 가능 여부는 다를 수 있습니다. 인증서 파일이 존재해도 서비스 차단, 인증서 만료, CA 키 침해·중지 등에 따라 거부될 수 있습니다. 서비스 전체 차단은 `서비스·에이전트` 화면에서 수행합니다.

<a id="manual-admin-agents"></a>

### 4.5 서비스·에이전트 → 에이전트

![에이전트 목록 — 등록 전 빈 목록 예시](docs/screenshots/console/19-admin-agents.png)

이 탭은 등록을 완료한 Agent를 확인하고 접근 상태를 관리하는 화면입니다. 처음에는 목록이 비어 있을 수 있습니다. `서비스 등록` 버튼은 Application용이므로 Agent를 만들 때 사용하지 않습니다.

1. **등록 토큰 생성**에서 대상 유형을 `에이전트`로 선택합니다.
2. 등록할 Agent ID에 맞는 토큰을 생성합니다.
3. Agent 호스트의 설정에 서버 주소, Agent ID, 등록 토큰, 신뢰할 CA 파일을 적용합니다.
4. Agent를 실행합니다. Agent가 자체 개인키·CSR을 생성하고 서버에서 인증서를 발급받아 등록을 완료합니다.
5. 이 탭을 새로고침하여 Agent가 나타나는지 확인합니다. `인증서`에서도 발급 결과를 확인합니다.
6. 차단이 필요한 경우 대상 행의 차단 동작을 사용합니다. 재활성화 후에는 기존 인증서가 회복되지 않으므로 다시 등록해야 합니다.

Agent 호스트 파일 배포와 설정 예시는 아래 [Agent 배포 절차](#agent-배포-절차)를 참고하세요. 일반 사용자 포털은 Agent 등록을 대행하지 않습니다.

<a id="manual-admin-tokens"></a>

### 4.6 서비스·에이전트 → 등록 토큰

![등록 토큰 목록 — 아직 발급한 토큰이 없는 상태](docs/screenshots/console/20-admin-tokens.png)

**목적:** 프로그램의 최초 등록용 토큰을 발급하고 회수합니다. 여기서 만든 토큰으로 웹 화면에 로그인할 수 없습니다. 일반 사용자의 CSR 검토 방식으로 발급하는 경우에는 이 토큰을 추가로 발급할 필요가 없습니다.

![등록 토큰 생성 — 대상 유형·식별자·유효시간·사용 횟수](docs/screenshots/console/21-admin-token-dialog.png)

| 입력 | 어떻게 입력하나요? |
|---|---|
| 대상 유형 | Agent면 `에이전트`, Application 등록 API용이면 `애플리케이션` |
| 대상 식별자 | 등록할 Agent ID 또는 이미 등록한 서비스 ID와 일치 |
| 토큰 이름 | 용도를 구분할 이름. 예: `agent-seoul-01-initial` |
| 유효시간(초) | 기본 입력값 `3600`은 1시간. 화면 허용 범위는 60~604800초 |
| 최대 사용 횟수 | Agent용은 1~100회. Application용은 입력값과 관계없이 1회 |

1. **등록 토큰 생성**을 누르고 위 항목을 입력합니다.
2. 확인·MFA 절차 후 실행합니다. 창이 길면 안쪽을 아래로 스크롤합니다.
3. 발급 직후 나타나는 **토큰 원문을 안전하게 대상 프로그램 담당자에게 전달**합니다. 이때 한 번만 표시되며 목록에서 다시 볼 수 없습니다.
4. **확인 후 닫기**를 누릅니다.
5. 목록에서 참조 ID, 유형, 등록 대상, 만료일, 사용·회수 상태를 확인합니다. 사용 횟수 숫자는 이 목록에 별도로 표시되지 않습니다.
6. 사용하지 않을 토큰은 **회수**를 누르고 확인합니다. 토큰 회수는 앞으로 그 토큰을 이용한 등록을 막는 동작입니다. 이미 발급된 인증서까지 차단하려면 대상 서비스·Agent의 차단 절차를 검토합니다.

토큰 원문을 잃어버렸다면 목록에서 복원할 수 없습니다. 필요하면 기존 토큰을 회수하고 새로 발급합니다. 실제 토큰을 보고서나 스크린샷에 남기지 않습니다.

<a id="manual-admin-keys"></a>

### 4.7 키 관리 → 개요

![키 관리 개요 — 다음 교체를 위해 준비된 CA v2](docs/screenshots/console/10-admin-keys-overview.png)

**목적:** 어떤 서명 키가 있고 현재 어느 버전을 사용하는지 확인합니다. 조회에는 `AUDITOR`와 해당 키 범위, 변경에는 `KEY_ADMIN` 등이 필요합니다.

1. 왼쪽 **키 관리**를 엽니다.
2. 목록에서 **키 이름과 버전을 함께 확인**하고 원하는 행을 누릅니다. 이름만 같다고 같은 버전이 아닙니다.
3. 오른쪽 **개요**에서 상태·알고리즘·저장 방식·생성일·서명 기한을 확인합니다.
4. `준비됨` 버전은 신뢰 자료 배포 후 **활성화 요청**을 할 수 있습니다.
5. `사용 중` 버전의 상세에는 현재 서명 버전인지 안내가 표시됩니다. 공개 정보는 **공개 인증서·키 다운로드**로 받습니다.
6. 필요한 경우 **권한**, **의존성** 탭으로 이동합니다.

| 키 이름 | 하는 일 |
|---|---|
| `ca-root` | 서비스·Agent·서버 TLS 인증서 발급에 사용하는 ECDSA P-256 CA 서명 키 |
| `update-signing` | Agent 업데이트 배포 파일의 Ed25519 서명 키 |

![현재 사용 중인 CA v1 — 현재 버전 표시와 긴급 조치](docs/screenshots/console/10b-admin-keys-active.png)

최신 버전이 항상 현재 사용 버전인 것은 아닙니다. 예시에서는 v2가 `준비됨`, v1이 `사용 중`입니다. 새 버전을 준비한 것만으로 서명에 사용하는 키가 바뀌지 않습니다. **긴급 중지**와 **침해 선언**은 서비스 인증과 서명에 영향을 주는 조치이므로 단순 화면 확인용으로 실행하지 않습니다. 자세한 순서는 [키 운영 절차](#manual-rotation)를 따릅니다.

<a id="manual-admin-grants"></a>

### 4.8 키 관리 → 권한

![키 권한 — 내부 서비스의 SIGN 권한](docs/screenshots/console/11-admin-keys-grants.png)

이 탭은 **같은 키 ID의 모든 버전**에 적용되는 내부 서비스의 `SIGN` 권한을 보여 줍니다. Application의 업무 권한과 다른 권한입니다.

1. 키를 선택한 상태에서 **권한**을 누릅니다.
2. 현재 서명할 수 있는 서비스 주체를 확인합니다. CA에는 `service:certificate-issuer`, `service:tls`, 업데이트 키에는 `service:update-signer`가 사용됩니다.
3. 추가하려면 **권한 추가 요청**, 회수하려면 해당 주체 옆 **회수 요청**을 누릅니다.
4. 대상 서비스 주체와 작업 사유를 확인하고 요청을 접수합니다.
5. 다른 보안 담당자가 `승인 요청`에서 승인하면 반영됩니다.
6. 다시 권한 탭을 새로고침하여 결과를 확인합니다. 회수하면 해당 주체가 그 키로 수행하던 서명 작업이 거부될 수 있습니다.

<a id="manual-admin-dependencies"></a>

### 4.9 키 관리 → 의존성

![키 의존성 — 현재 CA와 인증서·TLS 참조로 삭제가 차단된 예시](docs/screenshots/console/12-admin-keys-dependencies.png)

**목적:** 키를 삭제하기 전에 아직 필요한 곳이 있는지 확인합니다.

1. 키와 버전을 선택하고 **의존성**을 누릅니다.
2. **현재 서명 버전**이 `예 · 삭제 불가`라면 먼저 정상적인 키 교체가 필요합니다.
3. **살아 있는 의존성** 수와 각 참조의 종류·대상·만료시각을 확인합니다.
4. 인증서, TLS, 릴리스가 계속 사용 중이면 해당 사용처의 전환 또는 유효기간 종료가 선행되어야 합니다.
5. `BACKUP` 참조가 있으면 실제 외부 백업을 처리한 뒤 **제거 확인 요청**에 백업 참조와 증적을 입력합니다. 다른 담당자의 승인을 받아 반영합니다.
6. 현재 버전이 아니고 의존성이 해소되는 등 조건을 만족하면 **삭제 예약 요청**을 사용할 수 있습니다.

`제거 확인 요청`은 외부 백업 파일을 지우는 기능이 아닙니다. 실제 처리 완료의 근거를 등록하는 절차입니다. 삭제의 전체 순서는 [중지·삭제](#manual-key-retirement)를 참고하세요.

<a id="manual-admin-approvals"></a>

### 4.10 승인 요청 — 다른 담당자의 KMS 변경 승인

![승인 요청 — 대기 요청이 없는 실제 상태](docs/screenshots/console/15-admin-approvals.png)

이 화면은 키 활성화·재개·권한·삭제 등의 **KMS 변경 요청**을 처리합니다. 캡처 환경에는 대기 요청이 없어 빈 목록으로 표시됩니다. 요청이 만들어지면 다음 순서로 처리합니다.

1. 요청자와 **다른 개인**이 `SECURITY_OFFICER` 및 필요한 조회 역할·키 범위를 가진 계정으로 로그인합니다.
2. 왼쪽 **승인 요청**을 열고 대상 요청을 선택합니다. 키 이름·변경 종류·요청자로 검색할 수 있습니다.
3. 상세의 키와 버전, 작업, 요청자, 사유, 유효기간을 확인합니다.
4. **요청에 고정된 변경 내용**에서 대상 주체·배포 증적·백업 제거 증적 등 해당 작업의 값을 확인합니다. 이 화면에서 요청 내용을 편집하지 않습니다.
5. **내용 확인 후 승인**을 누르고 확인 창에서 현재 MFA 코드와 작업 확인을 입력합니다.
6. **확인 후 실행**을 누르면 서버가 현재 권한·상태·의존성을 다시 검사한 뒤 변경을 실행합니다.
7. 승인 완료 상태와 실제 키 상태를 확인하고 **감사 기록 확인**으로 처리 결과를 추적합니다.

요청 유효기간은 24시간입니다. 자기 요청, 권한 부족, 기한 만료이면 승인 버튼을 사용할 수 없습니다. 이 UI에는 KMS 변경 요청을 반려·수정하는 버튼이 없습니다. 잘못된 요청은 승인하지 말고 담당자와 정정 내용을 확인하여 새 요청을 만들고 기존 요청의 만료 여부를 관리하세요.

<a id="manual-admin-tls"></a>

### 4.11 서버 TLS — 서버 인증서 이력

![서버 TLS — 발급 CA 버전과 인증서 만료일](docs/screenshots/console/22-admin-tls.png)

1. 왼쪽 **서버 TLS**를 엽니다.
2. 이력에서 TLS 버전·발급 CA 버전·상태·만료일을 확인하고 행을 선택합니다.
3. 상세의 키 지문 SHA-256, 발급 CA ID와 버전, 만료일을 확인합니다.
4. 필요한 경우 **공개 인증서 다운로드**를 사용합니다.
5. CA 키를 교체했다면 실제 서버 TLS 파일 적용과 프로세스 반영 여부도 별도로 확인합니다.

이 화면은 이력 조회와 공개 인증서 다운로드를 제공합니다. 웹에서 TLS 개인키를 편집하거나 파일 적용·서버 재시작을 실행하지 않습니다. **CA 활성화와 서버 TLS 적용은 별도 단계**입니다. 캡처에는 저장된 TLS v1 이력이 보이지만, 캡처 접속 자체는 로컬 검증용 HTTP이므로 이 기록만으로 현재 접속이 HTTPS라고 판단하면 안 됩니다.

<a id="manual-admin-releases"></a>

### 4.12 업데이트 서명 → 릴리스

![업데이트 서명 — 등록 전 릴리스 목록](docs/screenshots/console/23-admin-releases.png)

**목적:** Agent에 배포할 실제 파일을 등록하고 현재 업데이트 키로 서명합니다. 변경에는 `OPERATOR`가 필요합니다.

![릴리스 등록 — 버전·대상 플랫폼·실제 배포 파일](docs/screenshots/console/24-admin-release-dialog.png)

1. 왼쪽 **업데이트 서명** → **릴리스**를 엽니다.
2. **릴리스 등록**을 누릅니다.
3. 버전, 운영체제(`linux`, `windows`, `darwin`), 아키텍처(`amd64`, `arm64`), 채널을 입력합니다. 채널 기본 입력은 `stable`입니다.
4. **배포 파일**에서 해당 플랫폼의 실제 산출물을 선택합니다. 단순 설명 파일이나 임의 파일을 대신 선택하지 않습니다.
5. 확인·MFA 절차 후 실행합니다. 서버로 파일이 전송되고 서명됩니다. 입력 창이 길면 하단으로 스크롤합니다.
6. 목록에서 버전·플랫폼·채널·크기를 확인합니다. 새 릴리스는 `초안(DRAFT)` 상태입니다.
7. 배포할 준비가 되면 해당 행의 **활성화**를 누르고 확인합니다. 그 다음 `배포 정책`에서 대상에게 제공할 버전을 설정합니다.
8. 더 이상 제공하면 안 되는 활성 릴리스는 **폐기**합니다. 폐기한 릴리스는 재활성화할 수 없습니다.

릴리스 파일의 서명 키가 중지·침해 상태이면 배포 정책이 활성화되어 있어도 제공이 차단됩니다. 새 버전을 업로드하는 것, 릴리스를 활성화하는 것, Agent가 실제로 업데이트를 완료하는 것은 각각 다른 단계입니다.

<a id="manual-admin-policy"></a>

### 4.13 업데이트 서명 → 배포 정책

![배포 정책 — 적용값 조회와 정책 변경 진입](docs/screenshots/console/25-admin-release-policy.png)

![배포 정책 입력 — 전체 기본값 또는 특정 에이전트 지정](docs/screenshots/console/26-admin-policy-dialog.png)

1. **배포 정책** 탭 → **정책 변경**을 누릅니다.
2. 특정 Agent만 대상으로 할 경우 **에이전트 ID**를 입력합니다. **비우면 전체 기본 정책**을 변경합니다.
3. **배포**를 `활성화` 또는 `중지`로 선택합니다.
4. **채널**을 릴리스에 지정한 값과 맞춥니다.
5. **목표 버전**을 입력하면 해당 버전을 목표로 하고, 비우면 조건에 맞는 최신 버전을 사용합니다.
6. 확인·MFA 절차 후 실행하고 목록에서 실제 반영값을 확인합니다.
7. **배포 이력**에서 Agent별 진행 결과를 확인합니다.

한 대에 먼저 적용하려면 Agent ID를 반드시 지정하세요. 정책 변경은 Agent 프로세스가 즉시 완료되었다는 뜻이 아니며, Agent의 업데이트 확인과 실행 결과를 기다려야 합니다.

<a id="manual-admin-attempts"></a>

### 4.14 업데이트 서명 → 배포 이력

![배포 이력 — 아직 배포 시도가 없는 상태](docs/screenshots/console/27-admin-release-attempts.png)

**배포 이력** 탭을 열고 에이전트, 릴리스, 상태, 메시지, 갱신 시각을 확인합니다. **새로고침**으로 최신 기록을 불러옵니다. 실패 시 메시지를 확인하고 Agent 호스트 로그와 대상 플랫폼·파일·서명 키 상태를 함께 점검합니다.

목록이 비어 있다면 Agent 등록 여부, 활성 릴리스와 배포 정책, Agent의 서버 연결을 차례로 확인합니다. 이 화면에는 개별 배포를 강제로 다시 실행하는 버튼이 없습니다.

<a id="manual-admin-trust"></a>

### 4.15 신뢰 자료 — 공개 CA·업데이트 검증 키 배포

![신뢰 자료 — 번들 다운로드와 적용 순서](docs/screenshots/console/28-admin-trust.png)

1. 왼쪽 **신뢰 자료**를 엽니다.
2. 인증서 검증용이면 **CA 신뢰 번들**, 업데이트 서명 검증용이면 **업데이트 검증 키**를 다운로드합니다.
3. 지문과 대상 버전을 확인합니다. 번들에는 준비·사용 중·검증 전용인 공개 버전이 포함될 수 있습니다.
4. 실제 검증 프로그램에 신구 공개 자료를 설치하고 reload·검증 결과를 확인합니다.
5. 키 활성화를 준비 중이면 이 배포 결과를 **활성화 요청의 신뢰 자료 배포 증적**에 기록합니다.

침해되거나 파기한 버전은 제공 번들에 포함하지 않습니다. 이미 외부 프로그램에 설치된 신뢰 자료를 콘솔이 자동으로 제거하지는 않으므로 외부 검증자에도 변경을 적용해야 합니다.

<a id="manual-admin-audit"></a>

### 4.16 감사 기록 — 누가 무엇을 했는지 확인

![감사 기록 — PREPARE_ROTATION 검색과 이벤트 상세](docs/screenshots/console/29-admin-audit.png)

1. 왼쪽 **감사 기록**을 엽니다.
2. 검색창에 수행자, 작업 이름, 요청 관련 문자열을 입력합니다. 캡처는 `PREPARE_ROTATION`으로 검색한 예시입니다.
3. 결과 필터에서 `전체 결과`, `SUCCESS`, `DENIED`를 선택합니다.
4. 순번이나 화살표를 눌러 상세를 엽니다. 시각·수행자·작업·결과와 상세 값의 요청 ID 등을 확인합니다.
5. 찾는 작업이 없으면 **다음 범위**로 이동합니다. **이전 범위**로 되돌아갈 수 있습니다.
6. **내보내기**로 현재 불러온 검색 결과를 CSV로 받습니다.

**검색과 내보내기는 현재 조회 범위에 한정됩니다.** 한 번에 최대 100건을 조회하므로 원하는 이벤트가 없다고 전체 기록에 없다고 판단하지 마세요. KMS 작업과 관리 HTTP 요청·응답은 별도 이벤트로 남을 수 있습니다. 상세 단계의 `ACCEPTED`는 최종 성공과 다르므로 후속 `SUCCESS` 또는 `DENIED`도 확인합니다. 감사 체인 무결성은 `운영 상태`에서 확인합니다.

<a id="manual-admin-health"></a>

### 4.17 운영 상태 — 키 사용과 저장소 상태 확인

![운영 상태 — 사용 불가 키·만료 임박·감사 이벤트 현황](docs/screenshots/console/30-admin-health.png)

1. 왼쪽 **운영 상태**를 엽니다.
2. **운영 가능** 여부와 확인 시각을 봅니다.
3. 사용 불가 현재 키 수, 30일 내 서명 기한 도래 수, 감사 이벤트 수, 서명 backend, 운영 모드를 확인합니다.
4. 키 문제가 있으면 **키 상태 확인**으로 이동하여 해당 버전과 서명 기한을 확인합니다.
5. 무결성·복구 문제라면 **복구 절차 확인**과 [KMS 운영 가이드](KMS_OPERATIONS.md)를 사용합니다.
6. 조치 후 **새로고침**으로 다시 확인합니다.

`운영 가능`은 현재 키·저장소 검사 결과이며 실제 HSM, 외부 서비스, 모든 Agent의 연결 시험 결과를 대신하지 않습니다. `development`가 보이면 개발 호환 모드입니다. 저장소 무결성 실패를 해결하려고 checkpoint를 지우거나 과거 값으로 낮추지 말고 운영자의 복구 절차를 따릅니다.

<a id="manual-rotation"></a>

## 5. 키 교체·중지·삭제 작업 순서

이 절차는 키 운영 담당자용입니다. 단순히 서비스 인증서를 발급받거나 갱신하는 사용자는 [일반 사용자 절차](#manual-user-enroll)를 따릅니다.

### 5.1 키 상태를 읽는 법

| 화면 표시 | 내부 값 | 의미 |
|---|---|---|
| 준비됨 | `PRE_ACTIVE` | 새 버전을 준비함. 신뢰 자료 배포와 활성화 승인 전 |
| 사용 중 | `ACTIVE` | 서명에 사용하는 활성 버전. 서명 기한·권한도 충족해야 함 |
| 검증 전용 | `VERIFY_ONLY` | 새 서명 대신 기존 인증서·서명의 검증을 유지하는 이전 버전 |
| 중지됨 | `SUSPENDED` | 사용이 중지됨. 재개는 별도 승인 필요 |
| 침해됨 | `COMPROMISED` | 침해가 선언됨. 재개 불가 |
| 삭제 예약 | `PENDING_DELETION` | 삭제 유예기간 진행 중. 바로 파기된 것이 아님 |
| 파기됨 | `DESTROYED` | 최종 파기 완료. 되돌릴 수 없음 |

### 5.2 새 버전 준비 → 신뢰 배포 → 다른 담당자 승인

![키 교체 준비 — 키 별칭과 작업 식별자](docs/screenshots/console/14-admin-rotation.png)

1. **현재 상태 확인:** `키 관리`에서 교체 대상의 현재 버전·서명 기한·의존성을 확인합니다. 키 담당자와 승인 담당자, 외부 검증자 배포 담당자의 역할을 정합니다.
2. **교체 준비 진입:** 키 목록 아래 **교체 준비**를 누릅니다.
3. **키 별칭 선택:** `ca-root` 또는 `update-signing` 중 실제 교체할 키를 명시적으로 선택합니다. 기본 선택이 대상과 같다고 가정하지 마세요.
4. **작업 식별자 확인:** 자동 생성된 값을 기록합니다. 같은 준비 작업의 응답을 받지 못해 재시도할 때는 동일한 ID를 유지합니다. 새 작업에 이전 ID를 재사용하지 않습니다.
5. **변경 내용 확인 → 확인 후 실행:** 필요한 MFA로 준비 작업을 실행합니다. 새 버전은 `준비됨(PRE_ACTIVE)`이 되고 현재 키는 계속 사용됩니다. HSM은 장비에서 사전 키 준비가 필요합니다.
6. **공개 자료 배포:** `신뢰 자료 보기` 또는 `키 관리 → 공개 인증서·키 다운로드`로 새 공개 자료를 확보합니다. 검증자에 신구 자료를 배포하고 reload·검증을 수행합니다.
7. **활성화 요청:** `키 관리`에서 **새 버전**을 선택하고 **활성화 요청**을 누릅니다. 배포 근거와 사유를 입력합니다.

![활성화 요청 — 신뢰 자료 배포 증적과 작업 사유](docs/screenshots/console/13-admin-activation-dialog.png)

| 입력 | 작성 예시 |
|---|---|
| 신뢰 자료 배포 증적 | `CHANGE-2026-101: gateway-a/b CA v2 지문 확인, 신구 번들 배포, reload 및 mTLS 시험 완료` |
| 작업 사유 | `현재 CA 서명 기한 도래 전 계획 교체` |

8. **다른 개인의 승인:** [승인 요청](#manual-admin-approvals)에서 별도 보안 담당자가 내용을 검토하고 MFA로 승인합니다.
9. **결과 확인:** 새 버전이 `사용 중`, 이전 버전이 `검증 전용`인지 확인합니다. 감사 기록과 운영 상태도 확인합니다.
10. **서비스 전환 확인:** CA 교체라면 서버 TLS 적용과 서비스 인증서 갱신도 별도로 수행합니다. 이전 인증서·서명을 검증할 필요가 남아 있는 동안 이전 공개 자료를 성급히 제거하지 않습니다.

증적은 확인된 실제 배포 결과를 적는 칸입니다. `확인`, `완료`라는 단어만 적는 것보다 변경 티켓·대상·버전·검증 결과를 남기는 것이 이후 검토에 도움이 됩니다. 토큰·개인키·MFA 비밀은 사유나 증적에 넣지 않습니다.

<a id="manual-key-retirement"></a>

### 5.3 긴급 중지·침해 선언·재개

| 작업 | 화면 경로 | 실행 결과와 후속 작업 |
|---|---|---|
| 긴급 중지 | 키 선택 → 개요 → **긴급 중지** | 사유·MFA·확인 후 해당 키 사용 중지. 정상화 후 별도 재개 요청 |
| 침해 선언 | 키 선택 → 개요 → **침해 선언** | 침해 상태로 전환하며 재개 불가. 외부 검증자에서 해당 신뢰도 제거하고 교체 절차 진행 |
| 재개 | 중지된 키 → 개요 → **재개 요청** | 다른 담당자의 승인과 서버 상태 검사 후 반영. 키 관리에서 최종 상태 확인 |

긴급 중지와 침해 선언은 확인 후 즉시 적용되는 긴급 조치이며 일반 승인 대기를 만드는 동작이 아닙니다. 적용하면 새 서명뿐 아니라 해당 CA 기반 인증서나 업데이트 검증에도 영향을 줄 수 있습니다. 정확한 대상 버전을 확인하고 영향받는 서비스 담당자와 조율합니다.

### 5.4 삭제 예약 → 유예기간 → 최종 파기

1. `키 관리 → 의존성`에서 **현재 버전이 아닌지**, 유효한 인증서·TLS·릴리스·백업 참조가 남지 않았는지 확인합니다.
2. 백업 참조가 있으면 외부 백업 처리와 증적 확보 후 **제거 확인 요청**을 별도로 승인받습니다.
3. 조건을 충족한 대상에 **삭제 예약 요청**을 만들고 다른 보안 담당자가 승인합니다.
4. 상태가 `삭제 예약`으로 바뀌고 삭제 예정 시각이 표시됩니다. 삭제 유예기간은 설정값을 따르며 최소 7일입니다.
5. 유예 종료 후 의존성이 다시 생기지 않았는지 확인합니다.
6. 소프트웨어 키는 **파기 요청**에서 백업 제거 증적과 사유를 입력하고 별도 승인을 받습니다. 최종 파기는 되돌릴 수 없습니다.
7. `파기됨` 상태와 감사 기록을 확인합니다. HSM 물리 키 파기는 장비 절차가 필요하며 이 화면에서 최종 물리 파기를 수행하지 않습니다.

잘못 예약했다면 대상 개요의 **삭제 취소**를 사용합니다. **취소 후에는 `중지됨`이 되며 자동으로 사용 재개되지 않습니다.** 재개가 필요하면 별도 재개 요청과 승인을 진행합니다.

<a id="manual-settings"></a>

## 6. 설정·구성 화면별 사용법

**이 메뉴는 현재 적용값과 운영 절차를 조회하는 화면입니다. 저장 버튼은 없습니다.** 값을 변경하려면 서버 운영자가 환경 변수·외부 설정을 수정하고 필요한 재시작과 상태 확인을 수행합니다. 이미 지정된 관리자·사용자 정책 파일의 내용은 매 요청마다 다시 읽습니다.

<a id="manual-settings-protection"></a>

### 6.1 키 보호

![설정·구성 — 키 보호](docs/screenshots/console/31-admin-settings-protection.png)

**설정·구성 → 키 보호**에서 CA·업데이트 서명 알고리즘, 저장 방식, 마스터 키 관리 형태, 환경·테넌트, 단일 writer 구성을 확인합니다.

1. 현재 소프트웨어 키 저장인지 PKCS#11 구성인지 확인합니다.
2. 마스터 키가 `개발용 로컬 보호 파일`이면 개발 구성이며, 운영용 외부 보호 파일과 구분합니다.
3. 구성을 변경할 때 [KMS 운영 가이드](KMS_OPERATIONS.md)의 환경 변수와 이관 절차를 사용합니다.
4. 재시작 후 이 화면과 `운영 상태`에서 반영 결과를 확인합니다.

마스터 키/wrapping key는 저장된 키를 여는 데 필요합니다. 기존 파일을 새 난수로 덮어쓰면 기존 저장소를 열 수 없습니다. 현재 재래핑 방식의 마스터 키 교체 API는 없습니다. 환경 이름도 기존 저장소에서 임의로 바꾸는 값이 아닙니다.

<a id="manual-settings-lifecycle"></a>

### 6.2 수명주기

![설정·구성 — 서명·인증서·삭제 유예기간](docs/screenshots/console/32-admin-settings-lifecycle.png)

**수명주기**에서 서명 유효기간, 인증서 유효기간, 삭제 유예기간, 승인 요청 유효기간, 서명 시도 한도와 상태 캐시를 확인합니다.

캡처 환경은 서명 365일, 인증서 30일, 삭제 유예 7일, 승인 요청 24시간, 키 ID당 분당 600회입니다. 배포 환경에서 변경될 수 있으므로 **실제 화면 값을 기준**으로 교체 일정을 잡습니다. 키의 서명 기한과 이미 발급된 개별 인증서 만료일은 다른 항목입니다. 서명 제한은 프로세스 내에서 적용됩니다.

<a id="manual-settings-identity"></a>

### 6.3 관리자·MFA

![설정·구성 — 관리자 역할·키 범위·MFA 정책](docs/screenshots/console/33-admin-settings-identity.png)

1. **관리자·MFA**를 선택합니다.
2. 관리자 개인 ID, 역할, 키 범위, 변경 작업 MFA 여부를 확인합니다.
3. 요청 담당자와 승인 담당자가 서로 다른 개인으로 구성되어 있는지 확인합니다.
4. 일반 사용자가 로그인하지 못한다면 **사용자 포털 정책**이 구성되어 있는지도 확인합니다.
5. 추가·회수·MFA 변경이 필요하면 서버 운영자가 외부 정책 파일을 관리합니다. 형식은 [KMS 운영 가이드](KMS_OPERATIONS.md)와 [콘솔 설치 안내](frontend/README.md)를 사용합니다.

이 화면은 토큰 원문이나 MFA secret을 보여 주지 않습니다. QR 코드 등록·토큰 재발급·계정 추가 버튼도 없습니다. 화면에 계정이 보인다고 해당 계정의 비밀 정보를 조회할 수 있는 것은 아닙니다.

<a id="manual-settings-backup"></a>

### 6.4 백업·복구

![설정·구성 — 오프라인 백업과 복구 순서](docs/screenshots/console/34-admin-settings-backup.png)

1. **백업·복구**를 선택합니다.
2. 백업 범위, 별도 보관 항목, 복원 대상과 검증 조건을 확인합니다.
3. **절차 안내 다운로드**로 `kms-backup-guide.txt`를 받습니다. **이 파일은 안내문이며 실제 백업 아카이브가 아닙니다.**
4. 서버 운영자는 서비스를 중지하고 [KMS 운영 가이드](KMS_OPERATIONS.md)의 CLI로 암호화 백업·복원을 수행합니다.
5. 복원 후 최신 외부 checkpoint 및 키·권한·침해·삭제 상태를 검증하고 서비스를 재개합니다.

백업은 data-dir 전체 스냅샷이며 최대 512 MiB입니다. wrapping key, 백업 키, 최신 checkpoint, 계정 정책은 별도로 보호 보관해야 합니다. 복원 대상은 원래 절대 경로의 빈 data-dir이며, 과거 스냅샷에 최신 상태를 자동으로 재적용하지 않습니다. 웹에서 실행 중인 서버를 온라인 복원하는 기능은 없습니다.

<a id="manual-settings-integration"></a>

### 6.5 HSM·모니터링

![설정·구성 — HSM과 외부 연동 범위](docs/screenshots/console/35-admin-settings-integration.png)

**HSM·모니터링**에서 PKCS#11 구성 유무, 업데이트 서명 backend, 외부 연동의 지원 범위를 확인합니다. **운영 상태 확인**을 누르면 현재 상태로 이동합니다.

| 항목 | 현재 UI·구현에서 알아둘 점 |
|---|---|
| PKCS#11 | CA P-256용 구성 확인. 장비·PIN·키 준비는 외부 운영 절차 |
| 업데이트 서명 | Ed25519 소프트웨어 backend |
| HSM 장애 | 소프트웨어 키로 자동 우회하지 않음 |
| SIEM / WORM | 별도 외부 수집·보존 연동 필요 |
| CRL / OCSP | 미구현 |
| 다중 노드 HA | 미지원; 단일 writer 구성 |

화면에서 `미구성`은 아직 해당 연동 설정이 없다는 의미이고 `미구현`·`미지원`은 현재 제품 기능 범위에 없다는 의미입니다.

## 7. 자주 발생하는 문제와 해결 방법

### 7.1 로그인·화면 접근 문제

| 증상 | 확인 순서 | 담당자에게 전달할 내용 |
|---|---|---|
| `Failed to fetch`, 연결 거부, 페이지를 열 수 없음 | 서버 실행 여부 → 정확한 주소·포트 → HTTP/HTTPS 일치 → 네트워크·인증서 신뢰 확인. 로컬 서버 종료가 흔한 원인 | 접속 URL, 발생 시각, 오류 문구 |
| 로그인 인증 오류 / 401 | 접속 구분 확인 → 올바른 토큰 **원문** 입력 → 접두사·따옴표·공백 제거 → 토큰 회수·교체 여부 문의 | 접속 구분과 계정 ID. 토큰 원문은 전달하지 않음 |
| 다시 로그인 화면이 나옴 | 유휴·최대 세션 만료 또는 정책 변경 여부 확인 후 재로그인 | 발생 시각, 반복 여부 |
| 메뉴가 없거나 403 | `내 계정`의 역할·키 범위 확인. 키 화면은 `AUDITOR`와 해당 키 범위 필요 | 계정 ID, 필요한 화면·키 |
| 일반 사용자의 서비스가 없음 | 관리자가 Application 등록했는지 → 사용자 정책 `services` 할당 확인 → 새로고침 | 계정 ID, 정확한 서비스 ID |
| 버튼이 회색임 | 권한, 선택 항목, 현재 상태, 자기 요청 여부, 만료, 의존성을 확인 | 화면·대상·현재 상태 |
| 새로고침 후에도 오류 화면 | 표시된 요청 ID 기록 후 운영 상태와 서버 로그 점검 | 요청 ID, 시간, 수행 작업 |

브라우저가 인증서 경고를 표시한다면 운영자에게 올바른 CA 신뢰 파일과 서버 이름을 확인받아 신뢰 구성을 해결합니다. 운영용 접속을 임의로 HTTP로 바꾸는 방식으로 해결하지 않습니다.

### 7.2 인증서 요청·다운로드 문제

| 증상 | 해결 방법 |
|---|---|
| CSR 입력이 거부됨 | 개인키가 아닌 `.csr`인지, PEM 시작·끝줄이 있는지, 64 KiB 이하인지 확인 |
| 서버에서 CSR 검증 실패 / 400 | EC P-256인지, CN이 서비스 ID와 같은지, `openssl req -in client.csr -noout -subject -verify`로 확인 |
| 중복 요청 / 409 | `내 요청`의 해당 서비스 대기 요청을 먼저 확인. 새로 반복 제출하지 않음 |
| 횟수 제한 / 429 | 반복 클릭을 중단하고 요청 한도와 이미 접수된 요청 확인. 제한 해제 후 진행 |
| 승인 대기가 계속됨 | 요청 ID와 서비스 ID를 운영자에게 전달하고 `인증서 요청 검토` 처리 요청 |
| 거절됨 | 상세의 검토 사유에 맞춰 수정하고 새 CSR 요청 |
| 다운로드 파일은 있는데 연결 실패 | 인증서에 맞는 개인키인지 → 만료·차단·현재 CA 상태 → 신뢰 번들 → 실제 서비스 TLS 설정 확인 |
| 다운로드 파일이 안 보임 | 브라우저 다운로드 목록·저장 위치 확인. 서버 오류가 표시됐으면 먼저 오류 해결 |
| 갱신 후 기존 인증서가 이전 인증서로 표시됨 | 새 인증서가 기존 것을 대체함. 새 파일과 그에 대응하는 개인키 적용 |
| 개인키를 잃어버림 | 콘솔에서 복원 불가. 새 개인키·CSR을 만들어 재발급 요청 |

### 7.3 관리자 변경·운영 문제

| 증상 | 해결 방법 |
|---|---|
| MFA 거부 | 현재 6자리 코드·서버와 기기 시각 확인. 같은 코드로 변경 작업을 재시도했다면 다음 코드 사용 |
| 키 활성화를 요청했는데 준비됨 상태 그대로 | `승인 요청` 접수만 완료된 상태일 수 있음. 다른 보안 담당자의 승인 확인 |
| 승인 버튼 비활성화 | 요청자와 동일 계정인지, `SECURITY_OFFICER` 역할인지, 24시간 기한이 지났는지 확인 |
| 승인 시 충돌 / 409 | 요청 이후 키 상태·권한·의존성이 바뀌었거나 이미 처리됨. 새로고침 후 현재 상태 기준으로 재검토 |
| 삭제 예약 버튼 비활성화 | 현재 서명 버전 또는 살아 있는 인증서·TLS·릴리스·백업 의존성 확인 |
| 최종 파기 버튼 비활성화 | 삭제 예정 시각 경과, 남은 의존성, HSM backend 여부 확인 |
| 서비스 차단 해제 후 연결 실패 | 기존 인증서는 자동 복구되지 않음. 새 등록·발급·적용 수행 |
| 설정에 저장 버튼이 없음 | 정상 동작. 현재값 조회 화면이므로 외부 설정과 운영 절차로 변경 |
| 안내문만 다운로드되고 백업이 안 됨 | `절차 안내 다운로드`는 텍스트 설명만 제공. 실제 백업은 서버 중지 후 CLI로 수행 |
| 릴리스 업로드가 거부됨 / 413 | 서버의 업로드 허용 크기와 실제 파일 크기를 운영자에게 확인 |
| 정책은 활성화인데 업데이트가 안 됨 | 릴리스 활성 상태 → 플랫폼·채널·목표 버전 일치 → 서명 키 상태 → Agent 연결·배포 이력 확인 |
| 감사 검색에 최근 작업이 안 나옴 | 검색은 현재 조회 범위만 대상. 필터 해제 후 다음 범위에서 확인 |
| 503 또는 무결성 검사 실패 | 정책 파일·HSM·키 저장소·로그를 서버 운영자가 점검. checkpoint나 키 파일을 임의 재생성하지 않음 |

문의할 때 **계정 ID, 서버 환경, 화면 이름, 대상 ID·버전, 시각, 오류 문구, 요청 ID**를 함께 남기면 원인을 찾기 쉽습니다. 토큰 원문·개인키·MFA 비밀은 제외합니다.

<a id="manual-server"></a>

## 8. 서버 실행 확인과 문서 안내

### 8.1 화면 사용과 서버 실행의 관계

콘솔은 정적 화면만으로 동작하지 않습니다. **CastrelSign Java 서버가 계속 실행 중이어야** 로그인·조회·발급이 가능합니다. 브라우저를 켜는 것만으로 서버가 자동 시작되지는 않습니다. 사용자는 서버가 꺼졌을 때 운영자에게 실행을 요청하고, 서버 운영자는 아래 사항을 확인합니다.

1. 기존 배포의 실행 명령·환경 변수·data-dir·포트를 확인합니다.
2. 같은 data-dir을 사용하는 서버 프로세스가 이미 실행 중인지 확인합니다. 같은 저장소를 여러 writer로 실행하지 않습니다.
3. 기존 설정으로 서버를 실행하고 시작 완료 로그를 확인합니다. 터미널에서 직접 실행했다면 그 프로세스를 종료할 때 서버도 종료됩니다.
4. 배포 주소의 `/console/`로 접속하여 로그인합니다.
5. `운영 상태`에서 키·저장소 상태를 확인합니다.

현재 PC의 로컬 검증 환경만 확인하려면 PowerShell에서 다음 **조회 명령**을 사용할 수 있습니다.

```powershell
# CastrelSign 디렉터리에서 실행: 로컬 검증 서버의 포트 확인
Get-NetTCPConnection -LocalPort 8444 -State Listen -ErrorAction SilentlyContinue

# 해당 검증 환경을 사용 중인 경우 시작·오류 로그 확인
Get-Content .\build\console-smoke\server.out.log -Tail 40
Get-Content .\build\console-smoke\server.err.log -Tail 40
```

결과가 없거나 파일이 없다면 이 검증 환경이 실행 중이거나 구성되어 있다고 가정하지 마세요. 운영 환경은 실제 서비스 관리자·로그 경로·포트를 사용합니다. 서버 재시작 시 기존 키 저장소의 경로·환경·보호 키를 그대로 유지해야 하므로, 새로운 data-dir을 만들어 로그인 문제를 우회하지 않습니다.

## 설치·개발·API 기술 참고

아래는 서버 운영자와 개발자를 위한 기존 기술 설명입니다. 화면 사용만 필요한 분은 위 설명서의 해당 절차를 이용하세요.

CastrelSign은 Castrelyx agent의 인증서 발급, mTLS 인증, agent ingest 수신을 담당하는 독립 Spring Boot 서브프로젝트입니다.

CastrelSign은 자체 self-signed root CA를 보유합니다. 이 root CA로 CastrelSign HTTPS server certificate를 발급하고, agent가 제출한 CSR을 서명해 agent client certificate를 발급합니다. agent private key는 agent 실행 호스트에서 생성되며, CastrelSign은 private key를 생성하거나 저장하거나 반환하지 않습니다.

현재 버전은 CA·업데이트 서명 키의 **인벤토리, 암호화 저장, 버전 교체, 상태·권한 검사, 2인 승인, 감사, 오프라인 백업·복원**을 제공합니다. 서버 TLS 키도 암호화 PEM·PKCS12로 저장하고 교체 이력을 관리합니다. 개발 기본 설정과 운영 설정의 보호 수준은 다릅니다. 구현 범위·검증 결과·남은 작업은 [구현 완료 보고서](implementation_report.md), 최초 요구사항은 [report.md](report.md), 구현 전 점검 결과는 [dev_report.md](dev_report.md)를 참고하세요.

**운영 설정·관리자 MFA·키 관리 API·교체·삭제·백업 명령은 [KMS 운영 가이드](KMS_OPERATIONS.md)에 있습니다.** 기본 `development` 모드는 개발 호환용입니다. 운영에서는 `CASTRELSIGN_KMS_MODE=production`과 외부 wrapping key·관리자 파일을 설정해야 합니다. 이관 후 평문 CA 키를 사용하는 구버전 서버로 즉시 되돌릴 수 없으므로 먼저 보호 백업을 확보하세요.

## KMS 관리 콘솔·사용자 포털

설계본을 실제 API와 연결한 구현은 **[frontend](frontend/README.md)**에 있습니다. `./gradlew bootJar`가 프런트엔드를 함께 빌드하고, 실행한 서버의 **`/console/`**에서 제공합니다. 빌드 환경에는 JDK 21, Node.js 22 이상과 npm이 필요합니다.

관리자 개인별 토큰 로그인, MFA 변경 작업, 키·승인·인증서·서비스·릴리스·감사·상태·설정 조회를 지원합니다. 일반 사용자는 `CASTRELSIGN_PORTAL_USERS_FILE`에 지정한 서비스 범위에서 CSR 제출, 요청 조회, 공개 인증서 수령을 수행합니다. 관리자는 새 **인증서 요청 검토** 화면에서 발급을 승인하거나 반려합니다. 요청·처리 이력은 DB에 저장합니다. 인증 설정과 사용자 파일 형식은 [콘솔 설치 안내](frontend/README.md), 실제 구현·검증·제약은 [UI 구현 보고서](console_implementation_report.md)를 참고하세요.

설정 화면은 현재 적용값과 운영 절차를 제공합니다. 외부 정책 파일, HSM, wrapping key, 백업·복원 변경은 [KMS 운영 가이드](KMS_OPERATIONS.md)의 절차를 따릅니다.

## 핵심 개념

| 항목 | 설명 |
| --- | --- |
| Root CA | CastrelSign이 최초 실행 시 생성하는 self-signed CA입니다. agent에는 `ca.pem`만 배포합니다. |
| Server certificate | root CA가 서명한 CastrelSign HTTPS 인증서입니다. agent는 `ca.pem`으로 이 인증서를 검증합니다. |
| Client certificate | root CA가 agent CSR을 서명해서 만든 agent mTLS 인증서입니다. EKU는 clientAuth입니다. |
| Enrollment token | admin API로 생성하는 agent 최초 등록용 bootstrap secret입니다. DB에는 hash만 저장되고, ingest/renew에는 사용하지 않습니다. |
| Admin token | Agent·Application·업데이트·키 관리용 관리자 자격 증명입니다. 운영에서는 개인별 token hash·역할·MFA를 사용합니다. |
| Agent private key | agent가 로컬에서 생성하는 ECDSA P-256 private key입니다. 서버로 전송하지 않습니다. |
| Ingest | agent가 gzip JSON batch를 `/api/agent/ingest`로 전송하는 수집 데이터 저장 경로입니다. |

## 실행 전 준비

필수 조건은 Java 21 이상과 Gradle입니다.

운영 실행에는 최소한 `CASTRELSIGN_PUBLIC_BASE_URL`과 `CASTRELSIGN_ADMIN_TOKEN`이 필요합니다. `CASTRELSIGN_PUBLIC_BASE_URL`은 agent가 접근할 수 있는 HTTPS 주소여야 합니다.

```powershell
cd D:\Study\castrelyx\CastrelSign

$env:CASTRELSIGN_PUBLIC_BASE_URL = 'https://manager.example.com:8443'
$env:CASTRELSIGN_ADMIN_TOKEN = 'replace-with-long-random-admin-token'
$env:CASTRELSIGN_TLS_SERVER_NAME = 'manager.example.com'

gradle bootRun
```

JAR로 실행할 때는 다음과 같이 사용할 수 있습니다.

```powershell
gradle bootJar

$env:CASTRELSIGN_PUBLIC_BASE_URL = 'https://manager.example.com:8443'
$env:CASTRELSIGN_ADMIN_TOKEN = 'replace-with-long-random-admin-token'
$env:CASTRELSIGN_TLS_SERVER_NAME = 'manager.example.com'

java -jar .\build\libs\CastrelSign-0.1.0.jar
```

## 설정

| 환경 변수 | 기본값 | 설명 |
| --- | --- | --- |
| `CASTRELSIGN_PORT` | `8443` | CastrelSign HTTPS listen port |
| `CASTRELSIGN_DATA_DIR` | `${user.home}/castrelsign` | CA, keystore, truststore, SQLite DB 저장 경로 |
| `CASTRELSIGN_PUBLIC_BASE_URL` | 없음 | enroll/renew 응답의 `ingest_url` 생성에 사용합니다. 운영 필수입니다. |
| `CASTRELSIGN_ADMIN_TOKEN` | 없음 | 개인별 관리자 파일이 없는 개발 모드의 공용 관리자 token. 운영에서는 사용하지 않습니다. |
| `CASTRELSIGN_ENROLLMENT_TOKEN` | 없음 | 이전 버전 호환용 설정입니다. production enrollment에는 사용하지 않습니다. |
| `CASTRELSIGN_CERT_VALID_DAYS` | `30` | server 및 agent client certificate 유효 기간 |
| `CASTRELSIGN_ROOT_VALID_DAYS` | `3650` | root CA 유효 기간 |
| `CASTRELSIGN_TLS_SERVER_NAME` | `localhost` | server certificate CN/SAN DNS 이름 |
| `CASTRELSIGN_KEYSTORE_PASSWORD` | `changeit` | TLS 암호화 PEM·PKCS12 비밀번호. 운영 모드에서는 16자 이상 필요 |
| `CASTRELSIGN_TLS_BOOTSTRAP_ENABLED` | `true` | generated CA/server TLS material과 기본 reloadable PEM bundle 구성. 외부 SSL identity를 완전히 제공할 때만 끕니다. |
| `CASTRELSIGN_SERVER_CERT_CHECK_INTERVAL_MS` | `3600000` | 실행 중 server certificate 갱신 검사 주기 |
| `CASTRELSIGN_SERVER_CERT_CHECK_INITIAL_DELAY_MS` | `60000` | 시작 후 첫 갱신 검사 지연 |

`CASTRELSIGN_TLS_SERVER_NAME`은 agent 설정의 `tls_server_name`과 일치해야 합니다. 예를 들어 agent가 `manager.example.com`으로 접속한다면 CastrelSign server certificate에도 `manager.example.com`이 SAN으로 들어가야 합니다.

## 최초 실행 시 생성되는 파일

CastrelSign은 최초 실행 시 `CASTRELSIGN_DATA_DIR` 아래에 다음 파일을 생성합니다.

| 경로 | 설명 | 배포 대상 |
| --- | --- | --- |
| `certs/ca.pem` | 준비·활성·검증 전용 CA 인증서 신뢰 묶음 | agent에 배포 |
| `kms/keys.sqlite` | 암호화 CA·업데이트 개인키 또는 HSM 참조, 정책·상태·감사 | 서버 내부 사용, 보호 백업만 허용 |
| `kms/initialized` | 저장소 유실 시 임의 재생성을 막는 초기화 표식 | 서버 내부 사용 |
| `secrets/kms-master.key` | 개발 모드 자동 생성 wrapping key. 운영에서는 외부 경로 지정 | 별도 보관, 절대 공개 배포 금지 |
| `certs/server.pem` | reloadable Spring Boot HTTPS server certificate | CastrelSign 내부 사용 |
| `certs/server.key` | 암호화 PKCS#8 서버 개인키, reloadable PEM bundle에서 복호화 | 외부 공개 배포 금지 |
| `certs/server.p12` | Logparser TCP/mTLS server keystore | CastrelSign/Logparser 내부 사용 |
| `certs/truststore.p12` | Logparser client certificate 검증용 truststore | CastrelSign/Logparser 내부 사용 |
| `castrelsign.sqlite` | SQLite 저장소 | CastrelSign 내부 사용 |

기존 `certs/ca.key`와 `update-signing/private.pem`은 공개키와 일치하는지 검사하여 KMS로 이관한 후 삭제합니다. 개인키 파일·DB·wrapping key를 Agent에 배포하지 않습니다. Agent 인증서 신뢰에는 `ca.pem`, 업데이트 검증에는 별도의 Ed25519 공개키 묶음을 배포합니다. wrapping key 옆의 `.checkpoint` 파일은 최신 감사 위치를 저장하며 백업과 별도로 보호합니다.

CastrelSign은 실행 중 매시간 server certificate와 PKCS12 정합성을 검사합니다. 설정된 유효기간의 마지막 1/3(최대 30일)에 들어오면 기존 root CA를 유지하고, 동일 CA 파일 잠금 아래 PEM pair는 transaction marker·atomic rename·directory fsync로, PKCS12 파일은 atomic replace로 갱신합니다. Spring Boot의 reloadable PEM bundle이 HTTPS connector를 재시작 없이 교체하며, Logparser는 PKCS12 변경을 감지해 TCP/mTLS listener를 다시 바인딩합니다. PKCS12가 유실되거나 한 번 기록에 실패해도 다음 검사에서 재생성합니다. Root CA는 신뢰 경계이므로 자동 교체하지 않습니다. 만료되었거나 새 leaf보다 먼저 만료되는 root는 명시적 trust migration 후 교체해야 합니다.

## 인증 모델

CastrelSign API는 두 단계 인증 모델을 사용합니다.

1. 최초 등록: enrollment token
2. 등록 이후: TLS client certificate

`/api/admin/enrollment-tokens`는 운영자가 enrollment token을 생성, 조회, 폐기하는 endpoint입니다. 이 endpoint는 `Authorization: Bearer <admin_token>`으로 보호됩니다.

`/api/agent/enroll`은 아직 client certificate가 없는 agent를 위한 endpoint입니다. 이 endpoint는 admin API로 생성된 `Authorization: Bearer <enrollment_token>`을 받습니다. CastrelSign은 token 원문을 저장하지 않고 SHA-256 hash, 만료 시각, 최대 사용 횟수, agent 제한, 폐기 상태를 DB에 저장합니다.

`/api/agent/renew`와 `/api/agent/ingest`는 Bearer token을 사용하지 않습니다. TLS handshake에서 제출된 client certificate가 있어야 하고, CastrelSign root CA로 검증되어야 합니다. 컨트롤러에서도 인증서 만료, root CA 서명, clientAuth EKU, subject CN을 확인합니다.

## 인증 흐름

```mermaid
sequenceDiagram
  participant Operator as 운영자
  participant Manager as CastrelSign
  participant Agent as Castrelyx Agent

  Operator->>Manager: CastrelSign 최초 실행
  Manager->>Manager: root CA, server cert, truststore 생성
  Operator->>Manager: POST /api/admin/enrollment-tokens + admin token
  Manager-->>Operator: enrollment token 원문 1회 반환
  Operator->>Agent: ca.pem, agent.yaml 배포
  Agent->>Agent: ECDSA P-256 client.key 생성
  Agent->>Agent: agent_id CN으로 CSR 생성
  Agent->>Manager: POST /api/agent/enroll + Bearer token + CSR
  Manager->>Manager: token, CSR 서명, CN=agent_id 검증
  Manager-->>Agent: ca_cert_pem, client_cert_pem, ingest_url
  Agent->>Agent: client.pem, enrollment.json 저장
  Agent->>Manager: POST /api/agent/ingest over mTLS
  Manager->>Manager: client cert CN과 batch source_id 매칭
  Manager-->>Agent: 202 Accepted
```

## Agent 배포 절차

### 1. CastrelSign 실행

CastrelSign을 먼저 실행해 root CA를 생성합니다.

```powershell
$env:CASTRELSIGN_PUBLIC_BASE_URL = 'https://manager.example.com:8443'
$env:CASTRELSIGN_ADMIN_TOKEN = 'replace-with-long-random-admin-token'
$env:CASTRELSIGN_TLS_SERVER_NAME = 'manager.example.com'
gradle bootRun
```

생성된 `ca.pem` 위치는 기본값 기준으로 다음과 같습니다.

```text
%USERPROFILE%\castrelsign\certs\ca.pem
```

### 2. Agent enrollment token 생성

agent별로 만료 시간이 짧고 사용 횟수가 제한된 enrollment token을 생성합니다.

```powershell
$body = @{
  name = 'host-001 initial enrollment'
  agent_id = 'host-001'
  ttl_seconds = 3600
  max_uses = 1
} | ConvertTo-Json

curl.exe --cacert .\certs\ca.pem `
  -H "Authorization: Bearer $env:CASTRELSIGN_ADMIN_TOKEN" `
  -H "Content-Type: application/json" `
  -d $body `
  https://manager.example.com:8443/api/admin/enrollment-tokens
```

응답의 `token` 값은 이때 한 번만 표시됩니다. 이 값을 agent 설정의 `enrollment_token`에 넣습니다.

### 3. Agent 설정 파일 준비

agent 설정 예시는 다음과 같습니다.

```yaml
manager_url: https://manager.example.com:8443
enrollment_token: cse_generated-token-from-admin-api
agent_id: host-001
tenant_id: default
cert_dir: ./certs
ca_cert_path: ./certs/ca.pem
tls_server_name: manager.example.com
batch_interval: 30s
spool_dir: ./spool
collectors:
  - identity
  - metric
  - network
  - process
  - service
  - port
```

`agent_id`는 인증서 subject CN이 되므로 안정적인 장비 식별자로 정해야 합니다. 이후 ingest batch의 `source_id`도 이 값과 같아야 합니다.

### 4. Agent 호스트에 파일 배포

agent 호스트에는 다음을 배포합니다.

| 파일 | 설명 |
| --- | --- |
| `agent.yaml` | agent 설정 |
| `certs/ca.pem` | CastrelSign root CA |

다음 파일은 최초 실행 후 agent가 로컬에서 생성하거나 저장합니다.

| 파일 | 생성 주체 | 설명 |
| --- | --- | --- |
| `certs/client.key` | agent | agent private key. 서버로 전송하지 않습니다. |
| `certs/client.pem` | CastrelSign 응답 저장 | agent client certificate |
| `certs/enrollment.json` | agent | `agent_id`, `ingest_url`, `expires_at` 메타데이터 |

### 5. Agent 최초 실행

agent는 `client.pem`이 없거나 만료된 경우 enrollment를 수행합니다.

1. `certs/client.key`가 없으면 ECDSA P-256 private key를 생성합니다.
2. `agent_id`를 CSR subject CN으로 넣어 CSR을 생성합니다.
3. `ca.pem`으로 CastrelSign HTTPS server certificate를 검증합니다.
4. `/api/agent/enroll`에 Bearer token과 CSR을 전송합니다.
5. 응답의 `client_cert_pem`을 `client.pem`으로 저장합니다.
6. 이후 ingest는 mTLS로 전송합니다.

## Agent 배포 후 인증서 인증 절차

agent 배포 후 정상 통신은 다음 절차로 인증됩니다.

1. agent가 CastrelSign에 TLS 연결을 시작합니다.
2. agent는 `ca.pem`으로 CastrelSign server certificate를 검증합니다.
3. `/api/agent/ingest` 또는 `/api/agent/renew` 호출 시 agent가 `client.pem`과 `client.key`를 사용해 client certificate를 제출합니다.
4. CastrelSign TLS layer가 `truststore.p12`에 들어 있는 root CA로 client certificate chain을 검증합니다.
5. 컨트롤러가 client certificate 존재 여부를 확인합니다.
6. 컨트롤러가 인증서 유효 기간과 root CA 서명을 다시 확인합니다.
7. 컨트롤러가 clientAuth EKU를 확인합니다.
8. 컨트롤러가 subject CN을 agent identity로 사용합니다.
9. ingest에서는 batch `source_id`가 subject CN과 같은지 확인합니다.
10. 검증이 끝나면 batch를 SQLite에 저장하고 `202 Accepted`를 반환합니다.

### `POST /api/admin/enrollment-tokens`

운영자가 agent 최초 등록용 enrollment token을 생성하는 endpoint입니다.

#### 인증

| 항목 | 값 |
| --- | --- |
| 방식 | Bearer token |
| 헤더 | `Authorization: Bearer <admin_token>` |
| mTLS client cert | 필요 없음 |

#### 요청 body

```json
{
  "name": "host-001 initial enrollment",
  "agent_id": "host-001",
  "ttl_seconds": 3600,
  "max_uses": 1
}
```

| 필드 | 필수 | 설명 |
| --- | --- | --- |
| `name` | 예 | 운영자가 식별할 token 이름 |
| `agent_id` | 아니오 | 지정하면 해당 agent만 이 token으로 enroll할 수 있습니다. production에서는 지정 권장 |
| `ttl_seconds` | 아니오 | token 만료 시간. 기본값은 86400초, 최소 60초입니다. |
| `max_uses` | 아니오 | 사용 가능 횟수. 기본값은 1입니다. |

#### 응답

```json
{
  "id": 1,
  "name": "host-001 initial enrollment",
  "token": "cse_xxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxx",
  "agent_id": "host-001",
  "max_uses": 1,
  "used_count": 0,
  "expires_at": "2026-06-07T12:00:00Z",
  "created_at": "2026-06-07T11:00:00Z"
}
```

`token` 원문은 생성 응답에서만 반환됩니다. DB에는 `token_hash`만 저장되고 list API에도 원문은 나오지 않습니다.

### `GET /api/admin/enrollment-tokens`

enrollment token 목록을 조회합니다. 응답에는 token 원문과 hash가 포함되지 않습니다.

#### 인증

| 항목 | 값 |
| --- | --- |
| 방식 | Bearer token |
| 헤더 | `Authorization: Bearer <admin_token>` |

#### 응답

```json
[
  {
    "id": 1,
    "name": "host-001 initial enrollment",
    "agent_id": "host-001",
    "max_uses": 1,
    "used_count": 1,
    "expires_at": "2026-06-07T12:00:00Z",
    "created_at": "2026-06-07T11:00:00Z",
    "last_used_at": "2026-06-07T11:05:00Z",
    "last_used_agent_id": "host-001"
  }
]
```

enrollment token을 폐기합니다. 폐기된 token은 남은 사용 횟수나 만료 시간과 관계없이 enroll에 사용할 수 없습니다.

#### 인증

| 항목 | 값 |
| --- | --- |
| 방식 | Bearer token |
| 헤더 | `Authorization: Bearer <admin_token>` |

#### 응답

정상 처리 시 body 없이 `204 No Content`를 반환합니다.

### `POST /api/agent/enroll`

client certificate가 아직 없는 agent의 최초 등록 endpoint입니다. 이 endpoint에서 사용하는 Bearer token은 admin API로 미리 생성한 enrollment token입니다.

#### 인증

| 항목 | 값 |
| --- | --- |
| 방식 | Bearer token |
| 헤더 | `Authorization: Bearer <enrollment_token>` |
| mTLS client cert | 필요 없음 |

#### 요청 헤더

| 헤더 | 필수 | 설명 |
| --- | --- | --- |
| `Authorization` | 예 | `Bearer <admin API로 생성한 enrollment token>` |
| `Content-Type` | 예 | `application/json` |

#### 요청 body

```json
{
  "agent_id": "host-001",
  "hostname": "host-001.example.com",
  "version": "0.1.0",
  "csr_pem": "-----BEGIN CERTIFICATE REQUEST-----\n...\n-----END CERTIFICATE REQUEST-----\n"
}
```

| 필드 | 필수 | 설명 |
| --- | --- | --- |
| `agent_id` | 예 | agent 고유 ID. CSR subject CN과 같아야 합니다. |
| `hostname` | 아니오 | agent 호스트명 |
| `version` | 아니오 | agent 버전 |
| `csr_pem` | 예 | agent private key로 서명한 PKCS#10 CSR PEM |

#### 검증

| 조건 | 실패 시 |
| --- | --- |
| Bearer token 누락 또는 hash 불일치 | `401 Unauthorized` |
| Bearer token 만료, 폐기, 사용 횟수 초과 | `401 Unauthorized` |
| Bearer token의 `agent_id` 제한과 요청 `agent_id` 불일치 | `403 Forbidden` |
| `agent_id` 누락 | `400 Bad Request` |
| `csr_pem` 누락 | `400 Bad Request` |
| CSR PEM 파싱 실패 | `400 Bad Request` |
| CSR subject CN 누락 | `400 Bad Request` |
| CSR subject CN과 `agent_id` 불일치 | `400 Bad Request` |
| CSR 서명 검증 실패 | `400 Bad Request` |
| CSR public key가 EC가 아님 | `400 Bad Request` |

#### 응답

```json
{
  "agent_id": "host-001",
  "ca_cert_pem": "-----BEGIN CERTIFICATE-----\n...\n-----END CERTIFICATE-----\n",
  "client_cert_pem": "-----BEGIN CERTIFICATE-----\n...\n-----END CERTIFICATE-----\n",
  "expires_at": "2026-07-07T00:00:00Z",
  "ingest_url": "https://manager.example.com:8443/api/agent/ingest"
}
```

| 필드 | 설명 |
| --- | --- |
| `agent_id` | 발급 대상 agent ID |
| `ca_cert_pem` | CastrelSign root CA PEM |
| `client_cert_pem` | agent client certificate PEM |
| `expires_at` | client certificate 만료 시각 |
| `ingest_url` | agent ingest endpoint |

#### curl 예시

```powershell
curl.exe --cacert .\certs\ca.pem `
  -H "Authorization: Bearer cse_generated-token-from-admin-api" `
  -H "Content-Type: application/json" `
  -d "@enroll-request.json" `
  https://manager.example.com:8443/api/agent/enroll
```

### `POST /api/agent/ingest`

agent가 수집 batch를 전송하는 endpoint입니다.

#### 인증

| 항목 | 값 |
| --- | --- |
| 방식 | mTLS client certificate |
| Bearer token | 사용하지 않음 |
| client certificate | 필수 |

#### 요청 헤더

| 헤더 | 필수 | 설명 |
| --- | --- | --- |
| `Content-Type` | 예 | `application/json` |
| `Content-Encoding` | 예 | `gzip` |

현재 구현은 `Content-Encoding: gzip`을 강제합니다. `Content-Type`은 클라이언트 계약상 `application/json`으로 보내야 합니다.

#### gzip 해제 후 body

```json
{
  "schema_version": "1.0",
  "source": "agent",
  "source_id": "host-001",
  "tenant_id": "default",
  "observed_at": "2026-06-07T00:00:00Z",
  "sent_at": "2026-06-07T00:00:01Z",
  "items": [
    {
      "kind": "metric",
      "type": "cpu",
      "key": "cpu.usage",
      "payload": {
        "value": 12.5,
        "unit": "percent"
      }
    }
  ]
}
```

| 필드 | 필수 | 설명 |
| --- | --- | --- |
| `schema_version` | 아니오 | batch schema version |
| `source` | 아니오 | 보통 `agent` |
| `source_id` | 예 | client certificate subject CN과 같아야 합니다. |
| `tenant_id` | 아니오 | tenant 식별자 |
| `observed_at` | 아니오 | agent 관측 시각 |
| `sent_at` | 아니오 | agent 전송 시각 |
| `items` | 아니오 | 수집 item 배열. 있으면 배열이어야 합니다. |

`items[]`는 다음 필드를 저장합니다.

| 필드 | 설명 |
| --- | --- |
| `kind` | `metric`, `event`, `state`, `log` 같은 상위 분류 |
| `type` | 세부 타입 |
| `key` | item key |
| `payload` | 원문 payload JSON |

#### 검증

| 조건 | 실패 시 |
| --- | --- |
| client certificate 누락 | `401 Unauthorized` |
| client certificate 만료 또는 서명 검증 실패 | `401 Unauthorized` |
| client certificate에 clientAuth EKU 없음 | `401 Unauthorized` |
| `Content-Encoding`이 `gzip`이 아님 | `415 Unsupported Media Type` |
| gzip 해제 실패 | `400 Bad Request` |
| JSON 파싱 실패 | `400 Bad Request` |
| body가 JSON object가 아님 | `400 Bad Request` |
| `items`가 배열이 아님 | `400 Bad Request` |
| `source_id` 누락 | `400 Bad Request` |
| `source_id`와 client certificate subject CN 불일치 | `403 Forbidden` |

#### 응답

정상 수신 시 body 없이 `202 Accepted`를 반환합니다.

#### curl 예시

```powershell
# Compress-Archive는 gzip이 아니므로 사용하지 마세요.

gzip.exe -c .\batch.json > .\batch.json.gz

curl.exe --cacert .\certs\ca.pem `
  --cert .\certs\client.pem `
  --key .\certs\client.key `
  -H "Content-Type: application/json" `
  -H "Content-Encoding: gzip" `
  --data-binary "@batch.json.gz" `
  https://manager.example.com:8443/api/agent/ingest
```

## Use Cases

### Use Case 1. CastrelSign 신규 설치

목표는 root CA와 HTTPS server certificate를 생성하고 manager를 실행하는 것입니다.

1. Java와 Gradle을 준비합니다.
2. `CASTRELSIGN_PUBLIC_BASE_URL`을 agent가 접근 가능한 HTTPS 주소로 설정합니다.
3. `CASTRELSIGN_ADMIN_TOKEN`을 충분히 긴 랜덤 값으로 설정합니다.
4. `CASTRELSIGN_TLS_SERVER_NAME`을 agent가 접속할 DNS 이름으로 설정합니다.
5. `gradle bootRun` 또는 `java -jar`로 실행합니다.
6. `CASTRELSIGN_DATA_DIR/certs/ca.pem`이 생성되었는지 확인합니다.

결과적으로 CastrelSign은 HTTPS로만 API를 제공합니다.

### Use Case 2. Agent 온라인 최초 등록

가장 권장하는 방식입니다.

1. 운영자가 agent 호스트에 `agent.yaml`과 `ca.pem`을 배포합니다.
2. 운영자가 admin API로 해당 `agent_id`에 제한된 enrollment token을 생성합니다.
3. agent 설정에 생성된 `enrollment_token`을 넣습니다.
4. agent를 최초 실행합니다.
5. agent가 `client.key`를 로컬 생성합니다.
6. agent가 CSR을 만들고 `/api/agent/enroll`에 제출합니다.
7. CastrelSign이 token 만료, 사용 횟수, agent 제한을 확인하고 token을 소비합니다.
8. CastrelSign이 CSR을 서명하고 `client.pem`을 반환합니다.
9. agent가 `client.pem`과 `enrollment.json`을 저장합니다.
10. 이후 agent는 mTLS로 ingest를 보냅니다.

이 방식에서는 private key가 agent 호스트 밖으로 나가지 않습니다.

### Use Case 3. Agent 사전 프로비저닝

네트워크가 제한된 환경에서는 agent 실행 호스트 또는 해당 호스트를 대표하는 안전한 프로비저닝 환경에서 미리 enrollment를 수행할 수 있습니다.

1. 대상 agent ID를 정합니다.
2. 대상 호스트에서 agent 또는 프로비저닝 도구가 private key와 CSR을 생성합니다.
3. 운영자가 admin API로 짧은 TTL의 enrollment token을 생성합니다.
4. CSR만 CastrelSign `/api/agent/enroll`로 제출합니다.
5. 응답으로 받은 `client.pem`, `ca.pem`, `enrollment.json`을 대상 host의 `cert_dir`에 둡니다.
6. agent 설정에서 `enrollment_token`은 제거할 수 있습니다.
7. agent는 시작 후 기존 `client.pem`과 `client.key`로 바로 mTLS ingest를 사용합니다.

주의할 점은 private key 생성 위치입니다. private key를 중앙 서버에서 만들어 여러 경로로 복사하는 방식은 권장하지 않습니다.

### Use Case 4. 정상 ingest

agent가 등록된 뒤 반복적으로 수행되는 일반 수집 흐름입니다.

1. agent가 collector를 실행해 수집 item을 만듭니다.
2. agent가 batch envelope를 JSON으로 구성합니다.
3. agent가 JSON을 gzip으로 압축합니다.
4. agent가 `client.pem`과 `client.key`로 mTLS 연결을 맺습니다.
5. agent가 `/api/agent/ingest`로 batch를 전송합니다.
6. CastrelSign이 client certificate CN과 batch `source_id`를 비교합니다.
7. CastrelSign이 batch 원문과 item을 SQLite에 저장합니다.
8. CastrelSign이 `202 Accepted`를 반환합니다.

### Use Case 5. 인증서 갱신

agent certificate 만료가 가까워지면 agent는 renew를 수행합니다.

1. agent가 기존 `client.pem`과 `client.key`로 mTLS 연결을 맺습니다.
2. agent가 같은 `agent_id`로 새 CSR을 생성합니다.
3. agent가 `/api/agent/renew`에 새 CSR을 제출합니다.
4. CastrelSign이 기존 client certificate CN과 요청 `agent_id`가 같은지 확인합니다.
5. CastrelSign이 새 CSR CN도 `agent_id`와 같은지 확인합니다.
6. CastrelSign이 새 client certificate를 발급합니다.
7. agent가 `client.pem`과 `enrollment.json`을 갱신합니다.

기존 인증서가 이미 만료된 뒤에는 `/api/agent/renew`가 실패합니다. 이 경우 운영자가 enrollment token을 사용해 재등록 절차를 수행해야 합니다.

### Use Case 6. Enrollment token 생성, 만료, 폐기

enrollment token은 개별 agent 등록용 bootstrap secret입니다.

1. 운영자가 `/api/admin/enrollment-tokens`로 agent별 token을 생성합니다.
2. production 기본값은 `agent_id` 지정, `max_uses=1`, 짧은 `ttl_seconds`입니다.
3. 생성 응답의 `token` 원문을 agent 설정에 넣습니다.
4. 등록이 끝나면 token은 사용 횟수가 소진되어 재사용되지 않습니다.
5. 등록 전 취소가 필요하면 `/api/admin/enrollment-tokens/{id}/revoke`로 폐기합니다.
6. 이미 등록된 agent는 enrollment token 없이 mTLS ingest/renew를 계속 사용합니다.

enrollment token만 폐기하면 기존 client certificate는 유지됩니다. `/api/admin/agents/{agentId}/block`은 Agent를 차단하고 ACTIVE 인증서와 사용 가능한 전용 token을 폐기합니다. Application 차단도 인증서와 미사용 token을 폐기하며, 재활성화 후에는 새로 등록해야 합니다.

### Use Case 7. Agent 재설치

agent 호스트를 재설치했지만 같은 `agent_id`를 유지하려는 경우입니다.

1. 기존 `client.key`와 `client.pem`이 백업되어 있고 안전하다면 그대로 복원합니다.
2. 키를 복원하지 못했다면 새 `client.key`를 생성하고 새 enrollment token으로 다시 `/api/agent/enroll`을 수행합니다.
3. 같은 `agent_id`로 새 인증서가 발급되면 `issued_certificates`에는 새 이력이 추가됩니다.

같은 `agent_id`의 새 인증서가 저장되면 기존 ACTIVE 인증서는 SUPERSEDED가 됩니다. 이전 serial을 이용한 renew·ingest는 거부됩니다.

### Use Case 8. 인증 실패 대응

| 증상 | 가능한 원인 | 조치 |
| --- | --- | --- |
| admin API가 `401` 반환 | admin token 누락 또는 불일치 | `CASTRELSIGN_ADMIN_TOKEN`과 요청 Authorization 헤더를 확인합니다. |
| enroll이 `401` 반환 | token 누락, 불일치, 만료, 폐기, 사용 횟수 초과 | agent 설정의 `enrollment_token`과 admin token 목록을 확인합니다. |
| enroll이 `403` 반환 | token이 다른 `agent_id`에 제한됨 | token 생성 시 지정한 `agent_id`와 agent 설정을 확인합니다. |
| enroll이 TLS 오류 | agent가 `ca.pem`을 신뢰하지 않음 | agent `ca_cert_path`와 `tls_server_name`을 확인합니다. |
| renew/ingest가 `401` 반환 | client cert 누락, 만료, 서명 불일치, EKU 누락 | `client.pem`, `client.key`, `ca.pem`을 확인합니다. |
| renew가 `403` 반환 | client cert CN과 요청 `agent_id` 불일치 | agent 설정의 `agent_id`를 인증서 CN과 맞춥니다. |
| ingest가 `415` 반환 | `Content-Encoding: gzip` 누락 | gzip 압축과 헤더를 확인합니다. |
| ingest가 `403` 반환 | batch `source_id`와 인증서 CN 불일치 | batch `source_id`를 agent ID와 맞춥니다. |

## SQLite 저장 구조

| 테이블 | 설명 |
| --- | --- |
| `enrollment_tokens` | enrollment token hash, agent 제한, 사용 횟수, 만료, 폐기 상태 |
| `agents` | agent identity, hostname, version, status, first/last seen |
| `issued_certificates` | agent별 발급 인증서 이력 |
| `ingest_batches` | batch envelope 필드와 raw JSON |
| `ingest_items` | batch `items[]`의 `kind`, `type`, `key`, `payload_json` |
| `audit_events` | enroll, renew, ingest 감사 이벤트 |

업무 데이터는 `castrelsign.sqlite`, 키 관리 데이터는 `kms/keys.sqlite`에 저장합니다. 원문 batch는 `ingest_batches.raw_json`에 저장하고, item 단위 조회를 위해 `ingest_items`에 주요 필드를 분리 저장합니다. 키 저장소의 키·정책·승인·의존성 변경과 감사 기록은 하나의 트랜잭션으로 커밋합니다.

## 보안 운영 기준

- 암호화 키 DB·TLS 개인키·wrapping key는 공개 배포하지 않습니다. 복구용 사본은 아래의 암호화 백업 절차를 사용합니다.
- agent에는 `ca.pem`만 배포합니다.
- agent private key는 agent 호스트에서 생성합니다.
- admin token은 모든 관리자 업무에 사용되며 agent에 배포하지 않습니다. 운영에서는 개인별 역할과 MFA가 필요합니다.
- enrollment token은 최초 등록용이며 ingest에는 사용하지 않습니다.
- enrollment token은 agent별로 제한하고, 짧은 TTL과 `max_uses=1`을 기본으로 사용합니다.
- enrollment token 원문은 생성 응답에서만 확인하고 DB에는 hash만 저장합니다.
- agent별 `agent_id`는 재사용과 충돌을 신중히 관리합니다.
- Agent·Application 내부 차단과 인증된 인증서 상태 조회 API를 제공합니다. CRL·OCSP와 외부 검증자 전체의 차단 자동 전파는 제공하지 않습니다.
- `CASTRELSIGN_KEYSTORE_PASSWORD` 기본값 `changeit`은 운영에서 변경해야 합니다.
