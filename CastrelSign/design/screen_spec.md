# CastrelSign KMS 전체 화면 상세 설계

작성일: 2026-09-24 · 버전: 화면 설계 1.0

## 요약

**관리자 20개, 사용자 7개, 공통 진입 1개, 총 28개의 화면·탭을 클릭 가능한 프로토타입으로 구체화했습니다.** 확정한 1번 시안의 관리자 목록+오른쪽 상세, 사용자 서비스 목록+인증서 상세 구조를 유지합니다. 형광색 없이 짙은 회색 배경과 제한된 청회색·녹회색·황갈색을 사용합니다.

| 구분 | 완성한 설계 | 운영 연결 상태 |
| --- | --- | --- |
| 관리자 업무 | 키·버전·권한·의존성, 교체, 2인 승인, 인증서, 서비스·에이전트, 등록 토큰, TLS, 릴리스, 신뢰 자료, 감사, 상태 | 핵심 백엔드 API 존재. 이번 결과물은 예시 데이터만 사용 |
| 설정·구성 | 키 보호, 수명주기, 관리자·MFA, 백업·복구, HSM·외부 연동 | 조회용 집계 API 필요. 파일/CLI 운영과 웹 적용을 구분 |
| 일반 사용자 | 내 서비스, 인증서, CSR 요청, 내 요청, 연결 가이드, 사용 이력, 내 계정 | 사용자 인증·소유권 모델·요청 워크플로 추가 개발 필요 |
| 공통 | 역할별 진입, 화면 목록, 로딩·빈 상태·오류·권한 없음, 검색, 상세, 확인 대화상자, 모바일 | 프로토타입 내 동작 구현 |

미리보기는 <http://127.0.0.1:4317/>입니다. 상단 **화면 목록**으로 전체 화면을 확인합니다. 데이터는 새로고침하면 초기화되고, 모든 변경 작업은 예시 상태만 바꿉니다. **데모 MFA는 `000000`**입니다.

여기서 “기존 API”는 해당 업무의 백엔드 기능이 있다는 뜻입니다. 웹 화면, 사용자 세션, 집계·필터·소유권 처리가 모두 구현됐다는 뜻은 아닙니다. 탭도 독립적인 검토 단위로 계산하며, 확인 대화상자는 28개에 추가로 포함됩니다.

## 2. 공통 구조와 역할

관리자는 상단 shell과 좌측 내비게이션을 사용합니다. 선택한 키는 오른쪽 패널에 표시하며 탭 전환 시 유지합니다. 일반 사용자는 상단 내비게이션에서 내 서비스·인증서·요청·가이드에 접근합니다. 계정과 사용 이력은 별도 화면으로 연결합니다.

`production · default`는 인스턴스의 고정 환경/테넌트 표시입니다. 현재 백엔드는 하나의 저장소를 대상으로 하므로 환경 전환 드롭다운을 제공하지 않습니다.

| 역할 | 주 업무 | 변경 제한 |
| --- | --- | --- |
| KEY_ADMIN | 키 교체 준비, 상태 변경, 권한·활성화·삭제 요청 | 자신의 요청을 직접 승인하지 않음 |
| SECURITY_OFFICER | 변경 내용·영향·증적 검토 후 승인 | 요청자와 다른 개인이어야 함 |
| AUDITOR | 허용된 키와 전역 감사·상태 조회 | 변경 버튼 비활성화 |
| OPERATOR | 서비스·에이전트·등록 토큰·업데이트 운영 | 키 수명주기 변경 권한과 분리 |
| 서비스 담당자 | 본인 서비스의 인증서 요청·수령·이력 | 소유권 기반 사용자 포털 API 필요 |

프로토타입의 역할 선택기는 검토 도구입니다. 실제 서비스에서는 서버가 각 요청의 개인 ID, 역할, 키 범위, 서비스 소유권을 검증해야 합니다. 모든 관리자 메뉴의 조회 범위를 정확히 제한하는 것은 운영 연동 단계의 작업입니다.

### 공통 상태

| 상태 | 표시와 동작 |
| --- | --- |
| 로딩 | 진행 표시와 설명. 운영 연결 시 이전 데이터의 조회 시각을 함께 표시 |
| 처음 방문/빈 목록 | 항목 없음과 다음 행동 안내. 검색 결과 없음과 구분 |
| 검색 결과 없음 | 검색어 지우기 또는 필터 변경 |
| 연결 오류 | 실패 안내 + 다시 시도. 알 수 없는 서버 상태를 정상으로 표시하지 않음 |
| 권한 없음 | 접근 불가 이유 + 담당자 문의 안내 |
| 변경 충돌 | 대상 상태가 변경됐음을 알리고 목록 재조회 후 새 요청 유도 |
| 작업 완료 | 상태 갱신 + 짧은 알림. 실제 연동에서는 서버 결과 재조회 |

상단 상태 선택기는 디자인 검토용으로 위 상태를 강제 표시합니다. HTTP 오류 분류, 세션 만료·재로그인, 429 재시도 시각, 감사 요청 ID 노출은 운영 연동 시 추가합니다.

## 3. 관리자 화면 명세

### A01–A05: 키와 승인

| ID / 경로 | 구성과 정보 | 주요 동작·제약 |
| --- | --- | --- |
| A01 `#keys` | 서명 만료 안내, 별칭·버전·용도·상태 표, 상세 패널의 알고리즘·보호 방식·생성일·서명 기한·수명주기 | 검색, 버전 선택, 공개 자료 보기, 교체 준비. 상태에 따라 활성화 요청/중지/재개/침해/삭제 취소 표시 |
| A02 `#keys?tab=grants` | 서비스 주체와 SIGN 권한 | 주체를 선택해 추가·회수 요청. CA는 certificate-issuer/tls, 업데이트는 update-signer. MFA와 다른 사람의 승인 필요 |
| A03 `#keys?tab=dependencies` | 유효 인증서 또는 릴리스 수, 외부 백업 참조, 현재 서명 버전 여부 | 현재 버전/살아 있는 의존성은 삭제 예약 금지. 예약 전 영향 확인. 백업 제거 증적 수집·검증은 운영 단계에서 연결 |
| A04 `#rotation` | 3단계: 별칭·작업 ID → 변경 요약·MFA → 신뢰 자료 배포 안내 | PRE_ACTIVE 준비. 같은 작업 재시도는 같은 requestId. 프로토타입은 준비된 버전이 있으면 선택; 전체 서버 멱등성 저장소는 재현하지 않음 |
| A05 `#approvals` | 왼쪽 요청 목록, 오른쪽 사유·요청자·만료·증적·변경 전후·처리 결과 | 다른 SECURITY_OFFICER만 승인. 승인 시 MFA 재입력. 처리 완료 후 재승인 버튼 제거. 감사 기록으로 이동 |

상세 패널의 목적은 목록에서 맥락을 잃지 않고 대상과 영향을 비교하는 것입니다. 불변 UUID, backend 세부 유형, allowed actions, 공용 PEM, 의존성 상세 식별자를 운영 응답에 맞춰 확장할 수 있습니다. 데모 목록은 주요 표시 필드와 예시 참조 개수에 집중합니다.

### A06–A15: 운영 업무

| ID / 경로 | 구성과 정보 | 주요 동작·제약 |
| --- | --- | --- |
| A06 `#certificates` | 발급 대상·일련번호·서명 버전·만료일·상태 목록과 상세 | 상태 다시 확인, 공개 인증서 안내 다운로드. ACTIVE/INACTIVE/UNKNOWN의 최종 판단은 상태 API 응답 사용 |
| A07 `#principals` | 애플리케이션 이름·유형·권한·상태 | OPERATOR의 차단/재활성화, 등록 토큰 생성. 재활성화 후 새 등록 필요. 신규 앱/권한 편집의 추가 폼은 운영 UI 확장 항목 |
| A08 `#principals?tab=agents` | 에이전트 식별자·접근 상태·업무 권한 | 인증서 목록으로 이동. 에이전트 자체 차단/재활성화 API는 존재하나 이 데모는 목록과 인증서 탐색 중심 |
| A09 `#principals?tab=tokens` | 토큰 참조·등록 대상·사용 횟수·만료·상태 | 생성 대화상자와 회수. 데모는 원문을 만들지 않음. 운영에서는 용도별 에이전트/앱 토큰 구분, TTL/maxUses 입력, 원문 1회 표시 필요 |
| A10 `#tls` | 현재 서버 인증서, 버전·발급 CA·알고리즘·만료·보호 방식·지문, 과거 이력 | 공개 인증서 보기. CA 활성화와 TLS 파일 적용 상태를 별개로 확인 |
| A11 `#releases` | 버전·플랫폼·서명 키·배포 상태 | 등록 → 초안 → 활성화 → 폐기. 폐기 후 재활성화 금지. 파일은 프로토타입 서버로 보내지 않음 |
| A12 `#releases?tab=policy` | 업데이트 배포 여부와 채널 | OPERATOR만 예시 정책 변경. 실제 agent별 정책 필드·배포 시도 목록은 기존 API 스키마에 맞춰 연결 |
| A13 `#trust` | CA 신뢰 번들, 업데이트 검증 공개키, 포함 버전, 외부 배포 절차 | 공개 자료 안내 다운로드. 준비/활성/검증 전용 버전만 포함. 실제 외부 설치·reload는 수동 확인 |
| A14 `#audit` | 순번·시각·수행자·작업·대상·결과; 검색과 결과 필터 | 이벤트 상세에서 요청 ID 확인, 현재 예시 행 CSV 내보내기. 실제 서버에서는 sequence 기반 추가 조회 |
| A15 `#health` | 현재 키 사용 불가 개수, 만료 예정 안내, 감사 이벤트, backend, 무결성·checkpoint 검사 | 다시 확인, 키 관리·복구 절차로 이동. 성공/정상은 화면에 예시라고 표시 |

목록 상세는 키·인증서·감사 항목에서 재사용합니다. 긴 식별자·fingerprint는 줄바꿈하고 원문 전체를 확인할 수 있어야 합니다. 프로토타입의 fingerprint와 일련번호는 실제 보안 자료가 아닌 예시 표시입니다.

### A16–A20: 설정·구성

좌측 분류 + 중앙 적용값 + 우측 운영 설명의 3영역입니다. 현재 서버에 없는 온라인 변경 API를 전제로 “저장 완료”를 표시하지 않습니다.

| ID / 경로 | 표시 항목 | 적용 방식 |
| --- | --- | --- |
| A16 `#settings` | CA/업데이트 알고리즘·backend, AES-256-GCM, 외부 wrapping key 사용, 테넌트/환경, single writer | 설정 변경 → 재시작 → 상태 확인. wrapping key 원문·파일 내용 표시 금지. 재래핑 API 없음 |
| A17 `#settings?tab=lifecycle` | 서명 365일, 인증서 30일, 삭제 최소 7일, 승인 24시간, 프로세스 내 분당 서명 한도, 상태 캐시 | 문서화된 기본 정책 조회. 실제 설정값 응답 API 추가 필요 |
| A18 `#settings?tab=identity` | 개인 ID, 역할, 키 범위, MFA 정책, 외부 관리자 파일 | 파일에서 관리. 토큰 hash·TOTP secret·복구 코드는 화면 응답에서 제외. 사용자 추가/역할 변경 폼은 제공하지 않음 |
| A19 `#settings?tab=backup` | 오프라인 순서, 512 MiB 제한, 별도 키·checkpoint 보관, 원래 절대 경로의 빈 저장소, 복원 검증 | CLI 운영 절차 안내. 백업 생성/복구를 실행하는 웹 버튼 없음 |
| A20 `#settings?tab=integration` | PKCS#11의 CA P-256 범위, 소프트웨어 Ed25519, 장비별 사전 준비, SIEM/WORM/CRL/OCSP/HA 지원 여부 | 미지원 기능은 연동 필요/미구현으로 표시. HSM 장애 시 소프트웨어로 자동 우회하지 않음 |

관리 API가 반환할 구성 DTO는 허용된 표시 필드만 담습니다. 임의의 환경변수, 전체 설정 파일, 파일 시스템 탐색을 UI에 노출하는 방식은 사용하지 않습니다.

## 4. 일반 사용자 화면 명세

| ID / 경로 | 구성과 정보 | 주요 동작·추가 개발 |
| --- | --- | --- |
| U01 `#services` | 내 서비스 목록, 선택 서비스의 인증서 만료·연결 상태, 갱신 단계, 최근 처리 | 검색, 선택, 갱신 요청, 공개 자료 다운로드, 요청 이력. 서버의 사용자–서비스 소유권 모델 필요 |
| U02 `#my-certificates` | 내 서비스에 발급된 인증서 목록과 상세 | 공개 인증서 수령·상태 확인. 관리자 전체 인증서 목록을 클라이언트에서만 필터링하지 않음 |
| U03 `#enroll` | 서비스 선택, CSR 파일/직접 입력 → 내용 확인 → 요청 완료 | 64 KiB 파일 제한, 개인키 표식 차단, 예시 CSR. 실제 CSR 서명·알고리즘·subject 검증은 서버 책임 |
| U04 `#my-requests` | 요청 번호·서비스·업무·등록 시각·승인 상태 | 상세에서 접수→검토→수령 단계 확인. 완료 예시는 공개 인증서 다운로드 가능. 요청 모델과 검토 API 추가 필요 |
| U05 `#guide` | CSR 준비→발급→신뢰 자료 설치; CA/업데이트 공개 자료 | 공개 자료와 안내 파일 다운로드. 지문 별도 확인, 로컬 개인키 보관, 외부 reload 안내 |
| U06 `#my-activity` | 내 서비스 업무 이력, 시각·대상·결과 | 필터·상세·예시 내보내기. 실제 운영에서는 서버에서 소유권으로 범위 제한 |
| U07 `#account` | 개인 ID, 역할, 환경, 접근 서비스 목록 | 데모 나가기. 비밀번호 변경·SSO 등록·관리자 권한 자가 신청 기능은 포함하지 않음 |

**사용자 CSR 요청의 검토함은 신규 설계입니다.** 기존 `/api/agent/enroll`, `/api/agent/renew`, `/api/applications/enroll`은 기계 등록 경로입니다. 이들이 곧바로 사람용 사용자 계정·승인함을 제공하는 것은 아닙니다. 데모에서 만든 CSR 요청은 KMS의 2인 키 변경 승인함에 들어가지 않습니다. 인증서 요청 검토 운영 화면/처리 API는 포털 구현 단계에서 별도로 추가해야 합니다.

### C01 `#login`

데모 역할 선택 화면입니다. 운영 로그인에는 조직 인증 또는 별도 인증 게이트웨이가 필요합니다. 이 프로토타입에서는 실제 계정·비밀번호·관리자 bearer token 입력란을 만들지 않습니다.

## 5. 주요 업무 흐름과 대화상자

### 키 교체·활성화

1. KEY_ADMIN이 별칭과 작업 ID를 선택합니다.
2. 변경 요약과 MFA 확인 후 PRE_ACTIVE 버전을 준비합니다.
3. 신구 공개 자료를 검증 대상에 배포하고 설치·reload 결과를 확인합니다. 화면에서 자동 배포 완료를 추정하지 않습니다.
4. 배포 증적, 사유, MFA, 영향 확인을 입력해 ACTIVATE를 요청합니다.
5. 다른 SECURITY_OFFICER가 변경 전후·요청자·만료를 검토하고 별도 MFA로 승인합니다.
6. 새 버전은 ACTIVE, 기존 현재 버전은 VERIFY_ONLY가 됩니다. 요청 결과와 감사 기록을 확인합니다.

같은 키/작업의 대기 요청이 있으면 기존 승인 목록으로 안내합니다. 실제 서버의 requestId 재사용·경합·24시간 만료·권한 변경 재검증은 서버 계약에 따릅니다.

### 긴급 중지·침해

대상 버전 → 영향 설명 → 사유 → MFA → 영향 확인 → 상태 변경 순서입니다. 긴급 중지는 SUSPENDED, 침해 선언은 COMPROMISED입니다. 침해된 키는 재개할 수 없습니다. 외부 검증자에서도 신뢰 제거가 필요하며, 키 상태 변경만으로 외부 신뢰 파일이 자동 갱신되지는 않습니다.

### 삭제

의존성 조회 → 살아 있는 인증서/릴리스/백업 정리 → 삭제 예약 요청 및 승인 → 최소 7일 유예 → 최종 파기 요청 및 별도 승인 순서입니다. 현재 서명 버전은 중지 상태여도 현재 버전인 동안 삭제 대상이 아닙니다. 삭제 취소 후 SUSPENDED를 유지하고 자동 활성화하지 않습니다.

데모의 최종 파기는 유예기간 미경과로 차단합니다. 운영 연결에서는 `ACK_BACKUP_PURGE` 요청에 백업 참조와 외부 제거 증적을 고정하고 별도 승인하는 추가 대화상자가 필요합니다. “파기”는 소프트웨어 암호문 제거와 tombstone이며 물리 매체 덮어쓰기 보장을 의미하지 않습니다. PKCS#11 장비의 물리 파기는 해당 장비 절차입니다.

### 서비스 차단

OPERATOR가 대상 서비스와 영향 안내를 확인하고 사유·MFA를 제출합니다. 기존 인증서와 미사용 등록 토큰이 회수되며, 재활성화는 새 등록이 필요한 상태로 돌아갑니다. 프로토타입은 서비스 상태 변경을 시뮬레이션하며 실제 회수 cascade는 실행하지 않습니다.

### CSR 요청

서비스 선택 → 서비스 환경에서 개인키/CSR 생성 → 공개 CSR 제출 → 내용 확인 → 접수 → 검토 → 공개 인증서 수령 → 서비스 적용 순서입니다. 개인키를 생성·다운로드하는 버튼은 제공하지 않습니다. 프로토타입은 표식 검증만 수행하며 실제 CSR로 사용할 수 없는 예시를 제공합니다.

### 공통 변경 대화상자

상단에 대상, 본문에 영향과 고정할 변경값, 하단에 사유·MFA·영향 확인, 마지막에 취소/실행 버튼을 둡니다. 위험 작업은 채도가 낮은 적색과 명확한 동사로 구별합니다. 네이티브 dialog로 포커스 영역을 제한하고 Escape/닫기 버튼으로 취소합니다. 운영 연동에서는 제출 중 중복 클릭 방지와 실패 시 재시도 기준을 추가합니다.

### 제안 API — 현재 존재하지 않음

다음 경로는 구현 계획을 논의하기 위한 예시이며, 프로토타입이나 기존 서버가 제공한다고 가정하지 않습니다.

| 제안 경로 | 책임 |
| --- | --- |
| `GET /api/console/me` | 서버 검증된 개인 ID·역할·서비스 범위·표시 가능한 기능 |
| `GET /api/console/configuration` | 허용 목록으로 구성한 비밀 없는 적용값·정책·지원 기능 |
| `GET /api/portal/services` | 현재 사용자에게 허용된 서비스만 반환 |
| `GET /api/portal/certificates` | 소유권 범위의 인증서·상태·공개 자료 참조 |
| `POST /api/portal/certificate-requests` | CSR 검증, 서비스 권한 확인, 요청 생성 |
| `GET /api/portal/requests` | 내 요청과 처리 상태 조회 |
| `GET /api/portal/activity` | 서버에서 범위를 제한한 사용자 업무 이력 |

인증서 요청의 승인·거절, 소유권 이전, 등록 토큰 전달 방식을 포함한 서버 계약을 포털 개발 전에 정해야 합니다. 기존 KMS 키 변경 2인 승인과 인증서 요청 검토의 정책을 혼합하지 않습니다.

### 브라우저 인증과 비밀값

브라우저용 인증 계층은 추가 개발입니다. 관리자 장기 bearer token을 localStorage에 보관하는 설계는 사용하지 않습니다. 운영 구현에서는 서버 측 인증 연결과 Secure/HttpOnly/SameSite 세션, CSRF 보호, 요청별 인가·MFA, 로그 마스킹을 함께 설계합니다. 클라이언트에서 버튼을 숨기는 것만으로 권한을 보장하지 않습니다.

## 7. 반응형·접근성

1440px에서는 관리자 목록/상세 두 열과 설정 세 영역을 사용합니다. 1000px 부근에서는 보조 설명을 아래로 이동하고 열 폭을 조정합니다. 980px 이하에서는 상세 패널이 목록 아래로 이동합니다. 760px 이하에서는 메뉴 버튼을 사용하고, 설정 분류는 가로로 스크롤됩니다.

모바일 표는 내용을 과도하게 줄이지 않고 **표 컨테이너 내부에서만 가로 스크롤**합니다. 페이지 전체가 가로로 밀리지 않습니다. 주요 버튼은 최소 38px, 모바일 40px입니다. 버튼·검색·필터·입력에 접근 가능한 이름을 제공하고 포커스를 표시합니다. 상태는 색상만으로 구분하지 않습니다.

정식 출시 전에는 스크린 리더, 키보드 전체 탐색, 고대비 모드, 실제 긴 식별자, 번역 길이, 큰 데이터 페이지를 추가 검증해야 합니다. 이번 작업에서 접근성 인증을 수행한 것은 아닙니다.

## 8. 완료 범위와 다음 구현 단위

완료: 28개 화면·탭의 레이아웃, 역할 미리보기, 검색과 상세, 대표 요청/승인/CSR 흐름, 오류 상태, 모바일 구성, 빌드와 브라우저 검증. 검증 증거는 [design-qa.md](prototype/design-qa.md)에 있습니다.

운영 제품으로 연결할 때는 다음 순서가 적절합니다.

1. 웹 인증·인가·MFA 계층과 API 응답 모델을 확정합니다.
2. 기존 API를 활용하는 키 조회·교체·승인·감사 화면을 연결합니다.
3. 서비스·에이전트 관리의 모든 폼, 토큰 원문 1회 표시, 업로드·배포 이력을 연결합니다.
4. 비밀값을 제외한 구성 조회 API와 운영 가이드를 연결합니다.
5. 사용자 소유권·CSR 검토 정책을 구현한 뒤 사용자 포털을 연결합니다.

이 화면 설계는 [KMS 요구사항](../report.md), [구현 전 점검](../dev_report.md), [구현 완료 보고서](../implementation_report.md), [운영 가이드](../KMS_OPERATIONS.md)를 기반으로 합니다. 백엔드의 완료 범위와 UI 제안 범위를 위와 같이 분리해 관리합니다.
